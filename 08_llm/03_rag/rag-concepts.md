# LLM & RAG 개념 정리

> 로컬 LLM 서버를 구축하면서 학습한 핵심 개념들을 정리한 문서입니다.

---

## 1. RAG란?

**RAG(Retrieval-Augmented Generation)** — 검색 기반 생성

LLM이 모르는 정보를 외부 문서에서 찾아서 답변하게 하는 기술입니다.

### 왜 필요한가?

LLM은 학습 시점 이후의 정보를 모르고, 회사 내부 문서도 당연히 모릅니다.

```
"우리 회사 2024년 매출 보고서 요약해줘" → LLM: 모릅니다
```

### 핵심 아이디어

**"LLM한테 시험 보기 전에 컨닝페이퍼를 쥐어주자"**

```
[RAG 없이]
사용자: "2024년 매출이 얼마야?"
LLM: "모릅니다" 또는 거짓말 (할루시네이션)

[RAG 있으면]
사용자: "2024년 매출이 얼마야?"
서버: 매출보고서.pdf에서 관련 내용 찾아서 LLM에 전달
LLM: "2024년 매출은 500억입니다" ← 문서 기반 정확한 답변
```

### 활용 예시

- 회사 내부 문서 기반 챗봇
- 수천 개 PDF 논문에서 질문에 맞는 답 찾기
- 최신 뉴스 기반 답변 AI

---

## 2. RAG 파이프라인

RAG는 두 가지 파이프라인으로 구성됩니다.

### 문서 저장 파이프라인 (한 번만 실행)

```
PDF/TXT 업로드
        ↓
텍스트 추출
        ↓
청크로 분할 (500자, overlap 50자)
        ↓
임베딩 모델로 벡터 변환
        ↓
Chroma(벡터 DB)에 저장
[ ID1 | 청크 텍스트 | 벡터 ]
[ ID2 | 청크 텍스트 | 벡터 ]
```

### 질문 답변 파이프라인 (질문마다 실행)

```
사용자 질문 입력
        ↓
질문을 벡터로 변환
        ↓
Chroma에서 유사도 높은 청크 top-k개 검색
        ↓
프롬프트 조립
┌─────────────────────────────┐
│ 아래 문서를 참고해서 답해줘  │
│                             │
│ 문서1: [청크 텍스트]         │
│ 문서2: [청크 텍스트]         │
│ 문서3: [청크 텍스트]         │
│                             │
│ 질문: [사용자 질문]          │
└─────────────────────────────┘
        ↓
Ollama(LLM)에 전달
        ↓
답변 반환
```

## 3. 청크(Chunk)

문서를 LLM에 통째로 넣으면 너무 길어서 오류가 납니다. 적당한 크기로 잘라야 합니다.

### 청크 크기

- 너무 작으면 → 문맥 부족
- 너무 크면 → 노이즈 증가, LLM 입력 한계 초과
- 보통 **500~1000자** 가 적당

### Overlap (겹침)

청크 경계에서 잘리는 문제를 방지하기 위해 앞 청크 내용 일부를 다음 청크에 포함합니다.

```
[Overlap 없이]
청크1: "철수는 서울 출신이다. 그는 2024년에 입사했으며"
청크2: "영업팀 소속이다. 현재 팀장을 맡고 있다"
→ 청크2만 검색되면 철수가 누군지 문맥 없음

[Overlap 있이]
청크1: "철수는 서울 출신이다. 그는 2024년에 입사했으며"
청크2: "그는 2024년에 입사했으며 영업팀 소속이다."  ← 앞 내용 포함
청크3: "영업팀 소속이다. 현재 팀장을 맡고 있다"     ← 앞 내용 포함
→ 어느 청크가 검색돼도 문맥이 이어짐
```

## 4. 임베딩(Embedding)과 벡터

### 왜 텍스트를 숫자로 바꾸나?

컴퓨터는 텍스트 간의 **의미적 유사도**를 직접 계산할 수 없습니다.

```
"강아지가 뛰어논다"
"개가 달린다"
```

사람은 비슷하다는 걸 알지만 컴퓨터는 글자가 다르면 다른 문장입니다.

### 벡터로 바꾸면

```
"강아지가 뛰어논다" → [0.8, 0.1, 0.9, ...]
"개가 달린다"       → [0.7, 0.1, 0.8, ...]  ← 숫자가 비슷 = 의미가 유사
"오늘 날씨 맑음"    → [0.1, 0.9, 0.2, ...]  ← 숫자가 다름 = 의미가 다름
```

### 벡터 공간 시각화 (2D 예시)

```
         동물 축
          ↑
   강아지 •  • 개
   고양이 •
          
          ───────→ 탈것 축
                • 자동차
                • 버스
```

실제로는 수백~수천 차원이지만 개념은 동일합니다.

### 문장 벡터 변환 원리

단어 하나하나의 벡터를 합산/평균해서 문장 전체의 벡터를 만듭니다.

```
"강아지가 뛰어논다"
= 강아지[0.8, 0.1] + 뛰어논다[0.5, 0.3] → 평균 → [0.65, 0.2]
```

실제 모델은 이보다 훨씬 정교하게 문맥까지 반영합니다.

## 5. 임베딩 모델

텍스트를 벡터로 변환해주는 AI 모델입니다.

```
임베딩 모델("강아지가 뛰어논다") → [0.8, 0.1, 0.9, ...]
```

### 종류

| 모델 | 차원 | 특징 |
|------|------|------|
| `nomic-embed-text` | 768 | 가볍고 빠름, Ollama 지원 |
| `mxbai-embed-large` | 1024 | 성능 좋음, Ollama 지원 |
| `bge-m3` | 1024 | 한국어 강점, 다국어 지원 |
| `text-embedding-ada-002` | 1536 | OpenAI 제공, 유료 |

한국어 문서를 다룰 경우 **bge-m3** 추천

### 중요 규칙

문서 저장할 때와 질문할 때 **반드시 같은 임베딩 모델**을 써야 합니다.
다른 모델을 쓰면 벡터 공간이 달라져서 유사도 검색이 엉터리로 됩니다.

## 6. Chroma (벡터 DB)

벡터를 저장하고 유사도 검색을 해주는 데이터베이스입니다.

### 기존 DB와 비교

| | RDB (PostgreSQL) | TSDB (InfluxDB) | Chroma |
|--|-----------------|-----------------|--------|
| 저장 단위 | 행/열 | 시계열 데이터 | 벡터 + 텍스트 |
| 검색 방식 | WHERE 조건 | 시간 범위 | 유사도 |
| 질문 형태 | "나이가 30인 사람" | "3시~5시 데이터" | "이 벡터와 비슷한 것" |

### 내부 구조

```
Collection (테이블 개념)
├── ID1 | "철수는 서울 출신..." | [0.8, 0.1, 0.9, ...] | {source: "사원명부.pdf"}
├── ID2 | "영업팀 소속이다..."  | [0.7, 0.2, 0.8, ...] | {source: "사원명부.pdf"}
├── ID3 | "매출은 120억..."     | [0.1, 0.9, 0.2, ...] | {source: "매출보고서.pdf"}
└── ID4 | "채용 공고..."        | [0.3, 0.4, 0.1, ...] | {source: "공고.pdf"}
```

### 유사도 검색 (코사인 유사도)

```
두 벡터가 같은 방향 → 유사도 1.0 (완전 동일)
두 벡터가 수직     → 유사도 0.0 (무관)
두 벡터가 반대 방향 → 유사도 -1.0 (반대)
```

### Chroma 쿼리

```python
# 저장
collection.add(
    ids=["ID1", "ID2"],
    documents=["철수는 서울 출신이다.", "매출은 120억이다."],
    embeddings=[[0.8, 0.1, 0.9], [0.1, 0.9, 0.2]],
    metadatas=[{"source": "사원명부.pdf"}, {"source": "매출보고서.pdf"}]
)

# 유사도 검색
results = collection.query(
    query_embeddings=[[0.75, 0.15, 0.85]],
    n_results=3  # top-k
)

# 필터링 (특정 파일에서만 검색)
results = collection.query(
    query_embeddings=[[0.75, 0.15, 0.85]],
    n_results=3,
    where={"source": "사원명부.pdf"}
)

# 삭제
collection.delete(ids=["ID1"])
```

### SQL과 비교

| SQL | Chroma |
|-----|--------|
| `INSERT INTO` | `collection.add()` |
| `SELECT WHERE` | `collection.query()` |
| `DELETE WHERE` | `collection.delete()` |
| `LIKE '%검색어%'` | `query_embeddings` 유사도 검색 |

### 다른 벡터 DB 비교

| DB | 특징 | 적합한 경우 |
|----|------|------------|
| **Chroma** | 가볍고 로컬 실행 쉬움 | 개발/중소규모 |
| **Pinecone** | 클라우드, 완전관리형 | 빠르게 프로덕션 |
| **Weaviate** | 기능 많고 확장성 좋음 | 대규모 |
| **pgvector** | PostgreSQL 확장 | 이미 PG 쓰는 경우 |
| **Qdrant** | 성능 좋고 필터링 강함 | 고성능 필요 시 |

## 7. top-k 검색

질문 하나에 벡터 ID 하나만 반환되는 게 아니라 **유사도 순으로 k개**가 반환됩니다.

```
질문: "철수 직책이 뭐야?"
        ↓
유사도 순위:
  1위 ID2 (거리 0.05) ← 가장 유사
  2위 ID1 (거리 0.08)
  3위 ID4 (거리 0.45)
        ↓
k=3이면 3개 모두 LLM에 전달
```

### k값 선택 기준

| k값 | 장점 | 단점 |
|-----|------|------|
| 작게 (1~2) | 빠름, 노이즈 적음 | 관련 내용 놓칠 수 있음 |
| 크게 (10+) | 더 많은 문맥 | LLM 입력 길어짐, 느려짐 |

보통 **k=3~5** 가 적당합니다.

## 8. LangChain

RAG, 에이전트 같은 LLM 앱을 만들 때 반복되는 작업을 미리 구현해둔 라이브러리입니다.

### 없으면 직접 짜야 하는 것들

```
PDF 읽기 → 청크 쪼개기 → 임베딩 모델 호출 →
Chroma에 저장 → 질문 임베딩 → 유사도 검색 →
프롬프트 조립 → LLM 호출 → 결과 파싱
```

### LangChain 있으면

```python
loader = PyPDFLoader("매출보고서.pdf")
docs = loader.load_and_split()
db = Chroma.from_documents(docs, embedding)
chain = RetrievalQA.from_chain_type(llm=llm, retriever=db.as_retriever())
chain.run("1분기 매출 알려줘")
```

### 단점

- 추상화가 많아서 내부 동작 파악이 어려움
- 버전 변경이 잦아서 코드가 자주 깨짐
- 간단한 RAG는 직접 짜는 게 더 깔끔

처음에는 LangChain으로 빠르게 만들어보고, 이후 직접 구현해보는 순서를 추천합니다.

## 9. RAG vs Fine-tuning

| | RAG | Fine-tuning |
|--|-----|-------------|
| 방식 | 외부 문서 검색해서 답변 | 모델 자체를 재학습 |
| 지식 업데이트 | 문서만 교체하면 됨 | 다시 학습해야 함 |
| 비용 | 낮음 | GPU 학습 비용 높음 |
| 적합한 경우 | 최신 정보, 사내 문서 | 말투/형식/도메인 특화 |

### RAG가 적합한 경우

```
"우리 회사 최신 공지사항 알려줘"
"2024년 4분기 보고서 요약해줘"
```

내용이 자주 바뀌어도 문서만 교체하면 됩니다.

### Fine-tuning이 적합한 경우

```
"법률 문서를 항상 이런 형식으로 작성해줘"
"의료 용어를 정확하게 이해하고 답해줘"
```

모델의 행동 자체를 바꾸고 싶을 때 사용합니다.

### 같이 쓰기도 함

```
Fine-tuning으로 말투/형식 학습
        +
RAG로 최신 문서 검색
```
