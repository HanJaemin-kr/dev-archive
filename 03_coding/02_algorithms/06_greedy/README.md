# 06. Greedy (그리디)

## 1. 그리디란?

**매 단계에서 가장 좋아 보이는 선택**을 누적해서 전체 최적해에 도달하는 알고리즘.
DP보다 빠르지만, **"그리디가 항상 옳지는 않다"** — 적용 가능 조건을 따져야 한다.

### 도식 — 그리디가 통할 때 vs 안 통할 때

```
   ✅ 통하는 예: 동전 [1, 5, 10, 25], amount = 30
       매번 큰 동전부터 → 25 + 5 = 2개 ✅ 최적

   ❌ 안 통하는 예: 동전 [1, 3, 4], amount = 6
       그리디: 4 + 1 + 1 = 3개
       최적:   3 + 3     = 2개  ← DP 가 답 발견
```

### 그리디가 성립하는 조건

```
   1. 그리디 선택 속성 (Greedy Choice Property)
       → 매 단계의 최선 선택이 전체 최적해의 일부.

   2. 최적 부분 구조 (Optimal Substructure)
       → 부분 문제의 최적해가 전체 최적해를 구성. (DP와 동일)
```

> **확신이 없으면 반례 먼저** — 작은 입력에서 그리디 vs 완전탐색을 비교해보고 통하면 그리디 채택.

## 2. 그리디 vs DP

| 항목 | 그리디 | DP |
|------|--------|-----|
| 접근 | 매 단계 최선 선택 | 모든 부분 문제 고려 |
| 시간 | 보통 O(n log n) | 보통 O(n²) 이상 |
| 적용 | 그리디 선택 속성 필요 | 거의 모든 최적화 |
| 증명 | 반례 없음을 보여야 함 | 점화식만 정확하면 됨 |

> 그리디가 통하면 압도적으로 빠르다. 안 통하면 DP 로.

## 3. JS 구현 템플릿

```js
// 일반적 골격: 정렬 → 순회 → 누적 선택
function greedy(items) {
  items.sort(compareFn);
  let result = 0;
  for (const item of items) {
    if (canTake(item)) {
      result += use(item);
      updateState();
    }
  }
  return result;
}
```

### 회의실 배정 (구간 스케줄링)

```js
function meetingRooms(meetings) {
  meetings.sort((a, b) => a[1] - b[1]);   // 종료 시간 오름차순
  let end = 0, count = 0;
  for (const [s, e] of meetings) {
    if (s >= end) { count++; end = e; }
  }
  return count;
}
```

## 4. 대표 패턴

### 패턴 A — 정렬 + 순회 그리디

```
   "회의실 배정" — 한 회의실에 최대한 많은 회의 배치

   종료 시간 기준 정렬:
       (1,4), (3,5), (0,6), (5,7), (3,8), (5,9), (6,10), ...

   왜 종료 시간?
     시작 시간 기준이면 긴 회의가 먼저 와서 다음 기회를 막음.
     종료 시간이 빠른 회의부터 잡아야 남은 시간 최대화.

   증명: "exchange argument" — 다른 어떤 선택보다 종료가 빠른 게 손해 없음.
```

용도: 구간 스케줄링, 활동 선택, 강의실 1개

### 패턴 B — 정렬 + 투 포인터

```
   "구명보트" — 보트 최대 2명, 무게 한계 limit

   정렬: [50, 50, 70, 80]
   lo=0, hi=3

   50+80=130 > 100 → 80만 → boats=1, hi--
   50+70=120 > 100 → 70만 → boats=2, hi--
   50+50=100 ≤ 100 → 둘 다 → boats=3, lo++,hi--

   "가장 무거운 사람"과 "가장 가벼운 사람"이 함께 탈 수 있으면 함께,
   아니면 무거운 사람만.
```

용도: 짝짓기 최소화, 부분 집합 그리디

### 패턴 C — MST (크루스칼)

```
   "최소 비용으로 모든 섬을 연결"

   1) 간선을 비용 오름차순 정렬
   2) Union-Find 로 사이클 없는 간선만 선택
   3) n - 1 개 선택하면 종료

   비용 [0-1:1, 1-3:1, 0-2:2, 1-2:5, 2-3:8]

       [0-1:1] 연결 → 1
       [1-3:1] 연결 → 2
       [0-2:2] 연결 → 4    ← n-1 = 3 개 완료
       [1-2:5] 사이클 → 스킵
```

```js
// Union-Find 골격은 10_graph 의 패턴 E 참고.
function kruskal(n, edges) {
  edges.sort((a, b) => a[2] - b[2]);
  const uf = new UnionFind(n);
  let cost = 0, used = 0;
  for (const [u, v, w] of edges) {
    if (uf.union(u, v)) { cost += w; used++; if (used === n - 1) break; }
  }
  return cost;
}
```

용도: 최소 신장 트리, 네트워크 연결 비용

### 패턴 D — 우선순위 큐 (힙 기반 그리디)

```
   "매번 최솟값/최댓값을 꺼내며 진행"

   - 회의실 배정 변형: 끝나는 시간이 가장 빠른 회의실을 다음 회의에 재할당
   - 작업 스케줄링: 데드라인 / 가치 기준 힙
   - 다익스트라: "현재까지 거리가 최소인 정점" 을 매번 pop
```

자세한 힙 패턴은 `01_data-structures/07_heap/README.md`.

용도: 동적으로 최솟값/최댓값 필요한 모든 그리디

### 패턴 E — 거스름돈류 (조건부 그리디)

```
   동전이 다음 조건을 만족하면 그리디 OK:
     큰 동전이 작은 동전의 정수배 (예: [1, 5, 10, 25, 100])

   조건 불만족 시 (예: [1, 3, 4]) 반드시 DP 사용.
```

용도: 한국/일반 화폐 단위, 정수 분할

## 5. 자주 하는 실수

- **그리디가 통한다고 확신 없이 진행** → 작은 입력에서 반례 검증을 먼저.
- **정렬 기준 모호** — "왜 종료 시간으로?" 같은 정당화가 안 되면 다른 기준 고려.
- **반례 검증 누락** → 거스름돈, 분할 문제는 특히 위험.
- **MST 에서 사이클 검사 누락** → Union-Find 필수.
- **우선순위 큐 안 쓰고 매번 정렬** → O(n² log n). 동적 추가/삭제는 힙.
