# 05. 애플리케이션 테스트 · 품질 · 형상관리 (빈출)

> 정보처리기사 실기(NCS 2020 개정) 단답/서술형 대비 빈출 노트.
> ⭐ = 최빈출. 텍스트 정확도 최우선 — **커버리지 강도 순서**와 **스텁/드라이버 구분**은 반드시 그대로 암기.

---

## 1. 화이트박스 테스트 ⭐ (White-box, 구조/코드 기반)

**개념**: 프로그램 **내부 구조·로직(소스 코드)**을 보고 테스트 케이스를 설계. "논리 흐름을 직접 검증". 개발자 관점.

**기법**
- **기초 경로 검사(Basis Path Testing)**: 대표 실행 경로 집합을 도출해 시험. McCabe. (순환복잡도 = E − N + 2)
- **제어 흐름 검사(Control Flow)**: 프로그램 제어 구조를 그래프로 표현해 검사.
- **데이터 흐름 검사(Data Flow)**: 변수의 **정의(define)–사용(use)** 관계를 추적.
- **루프 검사(Loop Testing)**: 반복 구조(단순/중첩/연결/비구조적 루프)를 집중 검사.

`자주 나오는 출제형태:`
- "소스 코드의 내부 논리 구조를 기반으로 하는 테스트 기법은?" → **화이트박스 테스트**
- "제어 흐름도에서 순환복잡도(Cyclomatic Complexity) 계산식은?" → **V(G) = E − N + 2** (E=간선, N=노드)

`핵심 답/암기:` **화이트박스 = 내부 구조 / 개발자 / 기초경로·제어흐름·데이터흐름·루프**

### 커버리지(Coverage) 강도 순서 ⭐ (약 → 강)

| 순위 | 커버리지 | 영문 | 정의(무엇을 100% 만족시켜야 하나) |
|------|----------|------|------------------------------------|
| ① 약 | 구문(문장) | Statement | 모든 **명령문(구문)**을 최소 1회 실행 |
| ② | 결정(분기) | Decision / Branch | 모든 **분기(전체 조건식)**의 참/거짓 결과를 각각 1회 이상 |
| ③ | 조건 | Condition | 분기 내 **개별 조건**의 참/거짓을 각각 1회 이상 |
| ④ | 조건/결정 | Decision/Condition | **결정 + 조건**을 모두 만족 (전체식 T/F & 개별조건 T/F) |
| ⑤ | 변형(수정)조건결정 | MC/DC | 개별 조건이 **독립적으로** 전체 결정 결과에 영향을 주는 경우를 검증 |
| ⑥ 강 | 다중 조건 | Multiple Condition | 개별 조건의 **모든 조합**을 검증 (가장 강함) |

> 암기 순서: **구문 → 결정(분기) → 조건 → 조건/결정 → MC/DC → 다중조건**.
> 함정: "결정 커버리지 = 분기 커버리지"(같은 말), "조건 커버리지가 결정 커버리지보다 항상 강하다"(**틀림** — 서로 포함 관계 아님).

`자주 나오는 출제형태:`
- "개별 조건식의 결과가 전체 결정에 독립적으로 영향을 주도록 하는 커버리지는?" → **MC/DC (변형조건결정)**
- "모든 문장을 최소 한 번 실행하는 가장 약한 커버리지는?" → **구문(Statement) 커버리지**

## 2. 블랙박스 테스트 ⭐ (Black-box, 명세/기능 기반)

**개념**: 내부 구조를 모르고 **입력↔출력(명세·기능)**만으로 테스트. "기능이 요구대로 동작하나". 사용자 관점.

| 기법 | 설명 |
|------|------|
| **동등 분할(동치 클래스, Equivalence Partitioning)** | 입력을 유효/무효 그룹으로 나눠 그룹당 대표값 하나 시험 |
| **경계값 분석(Boundary Value Analysis)** ⭐ | 경계(최소·최대·바로 안/밖)에서 오류 多 → 경계값 집중 |
| **원인-효과 그래프(Cause-Effect Graph)** | 입력(원인)과 출력(효과)의 논리 관계를 그래프화 |
| **오류 예측(Error Guessing)** | 경험·직관으로 오류 있을 만한 케이스 추정 |
| **비교 검사(Comparison Testing)** | 여러 버전에 같은 입력, 결과 비교 |
| **결정 테이블(Decision Table)** | 조건 조합과 그에 따른 행위를 표로 정리 |
| **상태 전이(State Transition)** | 상태 변화(이벤트→상태)를 검증 |
| **유스케이스(Use Case)** | 사용자 시나리오(업무 흐름) 기반 검증 |

`자주 나오는 출제형태:`
- "입력 조건의 경계가 되는 값에서 결함이 발생하기 쉬운 점을 이용하는 기법은?" → **경계값 분석**
- "입력 자료를 유효/무효 클래스로 나눠 대표값으로 시험하는 기법은?" → **동등(동치) 분할**

`핵심 답/암기:` **블랙박스 = 기능/명세 / 사용자 / 동등분할·경계값·원인효과·오류예측·비교·결정테이블·상태전이·유스케이스**

```
단위(Unit) → 통합(Integration) → 시스템(System) → 인수(Acceptance)
```

| **통합(Integration)** | 시스템(아키텍처) 설계 | 모듈 간 **인터페이스**·연동 검증 |
| **시스템(System)** | 요구사항/기능 명세 | 완성 시스템을 실제 환경에서 전체 검증(기능/비기능) |

- "개발자 관점의 통제된 환경에서 수행하는 인수 테스트는?" → **알파 테스트** / "사용자 현장에서 수행" → **베타 테스트**
- "모듈 간 인터페이스 오류를 확인하는 테스트 레벨은?" → **통합 테스트**

## 4. 통합 테스트 방식 ⭐ (스텁 vs 드라이버)

| 방식 | 방향 | 사용 모듈 | 특징 |
|------|------|-----------|------|
| **하향식(Top-down)** | 상위 → 하위 | **스텁(Stub)** ⭐ | 아직 없는 **하위 모듈**을 대신하는 더미. 상위 제어 로직 조기 검증 |
| **상향식(Bottom-up)** | 하위 → 상위 | **드라이버(Driver)** ⭐ | 아직 없는 **상위 모듈**을 대신해 하위를 호출·시험. 클러스터 단위 |
| **빅뱅(Big-bang)** | 동시 | (없음) | 모든 모듈을 한 번에 결합. 결함 위치 파악 어려움 |
| **샌드위치(Sandwich, 혼합)** | 상+하 동시 | 스텁+드라이버 | 하향식+상향식 병행 |

> **암기 핵심(단골 함정)**: **하향식 = Stub**, **상향식 = Driver**. (뒤바꾸는 문제 빈출)
> - **스텁(Stub)** = 하위 모듈을 흉내내는 **더미(호출당하는 쪽)** → 하향식.
> - **드라이버(Driver)** = 상위 모듈을 흉내내며 **하위를 호출하는 쪽** → 상향식.

- "하위 모듈부터 통합하며 상위 모듈을 대신하는 것은?" → **드라이버(Driver)** / 방식은 **상향식**

## 5. 테스트 오라클 (Test Oracle)

**개념**: 테스트 결과가 **참인지(맞는지)** 판단하는 **기준(기대값 제공 메커니즘)**.

| 오라클 | 설명 |
|--------|------|
| **참(True) 오라클** | 모든 입력에 대해 기대 결과 제공 (완전) — 항공·의료 등 중요 시스템 |
| **샘플링(Sampling) 오라클** | 특정(일부) 입력값에 대해서만 기대 결과 제공 |
| **휴리스틱(Heuristic) 오라클** | 일부는 참값, 나머지는 **추정(경험/직관)**으로 처리 (샘플링 개선) |
| **일관성 검사(Consistent) 오라클** | 변경 전/후 실행 결과가 **동일한지**로 판단 (회귀 테스트에 유용) |

`자주 나오는 출제형태:` "모든 입력값에 대해 기대 결과를 제공하는 오라클은?" → **참(True) 오라클**

## 6. 결함(Defect) 관련

**개념 — 오류→결함→고장 흐름**

| 용어 | 영문 | 의미 |
|------|------|------|
| **오류** | Error | 사람(개발자)의 **실수** (원인) |
| **결함/결점** | Fault / Defect / Bug | 오류로 인해 코드에 심어진 **잘못된 부분** |
| **고장/실패** | Failure | 결함이 실행되어 **명세와 다른 동작**으로 나타남 (결과) |

> 흐름: **사람의 Error → 코드의 Fault(Defect) → 실행 시 Failure**.

**결함 관리 프로세스**: 결함 등록 → 검토 → 할당(배정) → 수정(조치) → 조치 검토(확인) → 종료.

**결함 심각도(Severity, 영향 크기)**: 치명적(Critical) > 주요(Major) > 보통(Normal) > 경미(Minor) > 단순(Simple).
**결함 우선순위(Priority, 처리 순서)**: 긴급(Immediate) > 높음(High) > 보통(Medium) > 낮음(Low).

> 함정: **심각도 ≠ 우선순위**. 심각도=시스템에 미치는 영향, 우선순위=먼저 고칠 순서 (둘은 다를 수 있음).

`자주 나오는 출제형태:` "사람의 실수(Error) → ( ) → 실행 시 Failure. 괄호에 들어갈 용어는?" → **결함(Fault/Defect)**

## 7. 애플리케이션 성능 지표 ⭐

| 지표 | 영문 | 정의 |
|------|------|------|
| **처리량** | Throughput | 단위 시간당 처리하는 **작업/트랜잭션 수** |
| **응답 시간** | Response Time | 요청 후 **응답이 오기 시작**할 때까지 걸린 시간 |
| **경과 시간(반환 시간)** | Turnaround Time | 요청 후 **결과 출력이 완료**될 때까지 걸린 시간 |
| **자원 사용률** | Resource Utilization | 처리 중 **CPU·메모리·네트워크** 등 자원 사용 정도 |

`자주 나오는 출제형태:` "단위 시간당 처리하는 트랜잭션 수를 나타내는 성능 지표는?" → **처리량(Throughput)**

## 8. 테스트 커버리지 종류

- **기능 기반(Function) 커버리지**: 전체 기능 중 테스트된 기능의 비율(사용자 요구·유스케이스 기준).
- **라인(구문, Line/Statement) 커버리지**: 전체 코드 라인 중 실행된 라인 비율.
- **분기(Decision/Branch) 커버리지**: 전체 분기 중 실행된 분기 비율.

`자주 나오는 출제형태:` "코드의 각 라인이 실행되었는지를 기준으로 하는 커버리지는?" → **라인(구문) 커버리지**

## 9. 정적/동적 분석 & 검토 기법

| 구분 | 설명 |
|------|------|
| **정적 분석(Static)** | 프로그램을 **실행하지 않고** 코드·문서 자체를 분석 (리뷰, 정적 분석 도구) |
| **동적 분석(Dynamic)** | 프로그램을 **실행**하며 분석 (실제 테스트 수행) |

**검토(Review) 기법 — 정적 테스트**

| 기법 | 설명 |
|------|------|
| **인스펙션(Inspection)** | **공식적**·체계적 검토. 사전 준비 + 결함 목록 기록 (가장 엄격) |
| **워크스루(Walkthrough)** | 작성자 주도의 **비공식** 회의로 검토, 사전 검토 후 짧은 회의 |
| **동료 검토(Peer Review)** | 동료 2~3명이 개발자 설명을 들으며 결함 발견 |

`자주 나오는 출제형태:`
- "프로그램을 실행하지 않고 소스 코드를 분석하는 것은?" → **정적 분석**
- "공식적 검토 회의로 산출물을 검사하고 결함을 기록하는 검토 기법은?" → **인스펙션**

## 10. 형상관리 (SCM, Software Configuration Management) ⭐

**개념**: 소프트웨어 개발 중 발생하는 **산출물(코드·문서 등 형상 항목)의 변경**을 체계적으로 추적·통제해 **일관성과 무결성**을 유지하는 활동.

**형상관리 활동 5가지** ⭐

| 활동 | 영문 | 내용 |
|------|------|------|
| **형상 식별** | Identification | 관리 대상(형상 항목)을 정하고 이름·번호 부여 |
| **버전(형상) 관리** | Version Control | 산출물의 버전을 기록·관리 (도구 활용) |
| **형상 통제(변경 통제)** | Change Control | 변경 요청을 검토·승인/기각 (형상통제위원회 CCB) |
| **형상 감사** | Audit | 변경이 **올바르게 반영**되었는지, 베이스라인과 일치하는지 검사 |
| **형상 기록(상태 보고)** | Status Accounting | 형상의 변경 이력·상태를 기록·보고 |

> **베이스라인(Baseline)**: 특정 시점에 **공식 승인·합의된 기준 산출물**. 이후 변경은 반드시 **변경 통제 절차**를 거침. ("기준선")

`자주 나오는 출제형태:`
- "형상관리 활동 중, 정식으로 검토·합의되어 변경의 기준이 되는 산출물은?" → **베이스라인(Baseline)**
- "변경 요청을 검토·승인하여 통제하는 형상관리 활동은?" → **형상 통제(변경 통제)**
- "형상관리 활동 4~5가지를 쓰시오" → **식별 / 버전관리 / 통제 / 감사 / 기록(상태보고)**

### 형상관리 도구

| 유형 | 도구 | 특징 |
|------|------|------|
| **중앙집중형** | **CVS**, **SVN(Subversion)** | 중앙 서버 저장소 1곳. 서버 장애 시 작업 곤란 |
| **분산형** | **Git** | 개발자마다 **전체 저장소(로컬) 복제**. 오프라인 작업·빠름 |

**Git 기본 명령**

| 명령 | 기능 |
|------|------|
| `clone` | 원격 저장소를 로컬로 복제 |
| `add` | 변경 파일을 스테이징(Staging)에 추가 |
| `commit` | 스테이징 내용을 로컬 저장소에 기록 |
| `push` | 로컬 커밋을 **원격** 저장소로 반영 |
| `pull` | 원격 변경을 로컬로 가져와 **병합**(fetch+merge) |
| `branch` | 분기(브랜치) 생성·조회 |
| `merge` | 다른 브랜치 변경을 현재 브랜치로 병합 |

`자주 나오는 출제형태:`
- "개발자마다 저장소 전체를 복제해 사용하는 분산형 형상관리 도구는?" → **Git**
- "로컬 저장소의 커밋을 원격 저장소에 반영하는 Git 명령은?" → **push**

## 11. 소프트웨어 품질 표준

### ISO/IEC 9126 (→ 25010) 품질 특성 6가지 ⭐

| 특성 | 영문 | 의미 |
|------|------|------|
| **기능성** | Functionality | 요구 기능을 제공하는가 (정확성·상호운용성·보안성 등) |
| **신뢰성** | Reliability | 오류 없이 안정적으로 동작하는가 |
| **사용성** | Usability | 사용자가 쉽게 배우고 사용하는가 |
| **효율성** | Efficiency | 자원 대비 성능이 적절한가 |
| **유지보수성** | Maintainability | 수정·개선이 쉬운가 |
| **이식성** | Portability | 다른 환경으로 옮기기 쉬운가 |

> 암기: **기·신·사·효·유·이** (기능성·신뢰성·사용성·효율성·유지보수성·이식성).
> ISO/IEC **25010**은 9126을 대체·확장 (8특성: 위 6 + **보안성·호환성** 추가).

### 기타 품질/프로세스 표준

| 표준 | 내용 |
|------|------|
| **ISO/IEC 12207** | 소프트웨어 **생명주기(Life Cycle) 프로세스** 표준 |
| **CMMI** | Capability Maturity Model Integration — 개발 조직의 **성숙도 5단계** (초기→관리→정의→정량적관리→최적화) |
| **SPICE (ISO/IEC 15504)** | 소프트웨어 **프로세스 평가·개선** 국제 표준. 능력 수준 0~5단계(불완전→최적화) |
| **McCall 품질 요인** | 제품 운영·수정·전이 3관점 11개 품질 요인 (정확성·신뢰성·효율성·유지보수성·이식성 등) |

`자주 나오는 출제형태:`
- "ISO/IEC 9126의 품질 특성 6가지를 쓰시오" → **기능성·신뢰성·사용성·효율성·유지보수성·이식성**
- "소프트웨어 프로세스 성숙도를 5단계로 평가하는 모델은?" → **CMMI**
- "ISO/IEC 15504로도 불리는 프로세스 평가 표준은?" → **SPICE**

## 12. 리팩토링 · 클린코드 · 코드 스멜

| 용어 | 설명 |
|------|------|
| **리팩토링(Refactoring)** ⭐ | **기능(외부 동작)은 그대로** 두고 **내부 구조를 개선**해 가독성·유지보수성 향상 |
| **클린 코드(Clean Code)** | 읽기 쉽고 단순·중복 없는 코드 (가독성·단순성·의존성 최소·중복 최소·추상화) |
| **코드 스멜(Code Smell)** | 잠재적 문제를 암시하는 **나쁜 코드 징후**(중복 코드, 긴 메서드 등) → 리팩토링 대상 |

`자주 나오는 출제형태:` "외부 동작(기능)을 바꾸지 않고 내부 코드 구조를 개선하는 것은?" → **리팩토링**

## 13. 빌드 / CI 도구

| 유형 | 도구 | 특징 |
|------|------|------|
| **빌드 자동화** | **Ant** | XML 기반, 절차적(빌드 순서 직접 기술) |
| | **Maven** | XML(pom.xml), **의존성 관리** + 정형화된 빌드 생명주기 |
| | **Gradle** | **Groovy/Kotlin DSL** 스크립트, 유연·빠름(안드로이드 표준) |
| **지속적 통합(CI)** | **Jenkins** ⭐ | 커밋 시 자동 빌드·테스트를 수행하는 대표 **CI 서버** |

> **CI(Continuous Integration, 지속적 통합)**: 개발자 코드를 자주(수시로) 통합·빌드·테스트해 통합 오류를 조기에 발견.

`자주 나오는 출제형태:`
- "지속적 통합(CI)을 지원하는 대표적인 오픈소스 자동화 서버는?" → **Jenkins**
- "XML(pom.xml) 기반으로 의존성을 관리하는 빌드 도구는?" → **Maven**
