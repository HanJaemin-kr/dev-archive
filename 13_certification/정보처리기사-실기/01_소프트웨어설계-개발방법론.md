# 01. 소프트웨어 설계 · 개발방법론 (빈출)

> 정보처리기사 실기(NCS 2020 개정) 대비 이론 빈출 정리. 단답/서술 대비 — **답을 바로 외우는** 목적. 코드 출력 문제 제외.
> ⭐ = 최빈출 항목.

## 1. 응집도 (Cohesion) ⭐

`자주 나오는 출제형태:` 응집도 종류를 강→약 순서로 나열하시오 / 특정 설명이 어느 응집도인지 쓰시오.

`핵심 답/암기:`
- **높을수록 좋다(모듈 독립성 ↑).** 강 → 약 순서:
  **기능적 > 순차적 > 교환적(통신적) > 절차적 > 시간적 > 논리적 > 우연적**
- 암기: **기·순·교·절·시·논·우** (기순교절시논우)

| 응집도 | 설명 |
|--------|------|
| 기능적(Functional) | 모든 요소가 **단일 기능** 수행 (가장 강함, 이상적) |
| 순차적(Sequential) | 한 요소의 **출력이 다음 요소의 입력**으로 사용 |
| 교환적/통신적(Communicational) | **동일 입력·출력 데이터**를 사용하는 요소들 |
| 절차적(Procedural) | 요소들이 **정해진 순서(절차)**대로 수행 |
| 시간적(Temporal) | **특정 시점(초기화 등)**에 함께 실행되는 요소 모음 |
| 논리적(Logical) | **논리적으로 유사한** 기능을 묶음(선택 실행) |
| 우연적(Coincidental) | 요소 간 **관련 없음** (가장 약함, 최악) |

## 2. 결합도 (Coupling) ⭐

`자주 나오는 출제형태:` 결합도를 약→강 순서로 나열하시오 / 설명에 맞는 결합도를 쓰시오.

`핵심 답/암기:`
- **낮을수록 좋다(모듈 독립성 ↑).** 약 → 강 순서:
  **자료(Data) < 스탬프(Stamp) < 제어(Control) < 외부(External) < 공통(Common) < 내용(Content)**
- 암기: **자·스·제·외·공·내** (자스제외공내)

| 결합도 | 설명 |
|--------|------|
| 자료(Data) | **매개변수(파라미터)로 자료만** 전달 (가장 약함, 이상적) |
| 스탬프(Stamp) | **배열·구조체 등 자료구조** 전체를 전달 |
| 제어(Control) | 제어신호(**Flag 등**)를 전달해 상대 모듈 흐름 제어 |
| 외부(External) | **외부 장치/형식/통신 프로토콜** 등을 공유 |
| 공통(Common) | **전역 변수(공유 데이터)**를 여러 모듈이 참조 |
| 내용(Content) | 다른 모듈의 **내부 기능·데이터를 직접 참조** (가장 강함, 최악) |

## 3. GoF 디자인 패턴 23종 ⭐⭐ (최빈출)

`자주 나오는 출제형태:` 생성/구조/행위로 분류하시오 / 설명에 맞는 패턴명을 쓰시오 / 특정 패턴이 어느 분류인지.

`핵심 답/암기:` **생성 5 · 구조 7 · 행위 11**

### 생성 패턴 (5) — 객체 생성 방식
암기: **추·빌·팩·프·싱**

| 패턴 | 한 줄 설명 |
|------|-----------|
| Abstract Factory(추상 팩토리) | 관련·의존 객체군을 **묶어서** 생성(구체 클래스 노출 X) |
| Builder(빌더) | 복합 객체의 **생성 과정과 표현 분리**, 단계별 생성 |
| Factory Method(팩토리 메서드) | 객체 생성을 **서브클래스에 위임** |
| Prototype(프로토타입) | **원본 복제(clone)**로 객체 생성 |
| Singleton(싱글턴) | 클래스 인스턴스를 **하나만** 보장, 전역 접근 |

### 구조 패턴 (7) — 클래스·객체 결합
암기: **어·브·컴·데·퍼·플·프**

| 패턴 | 한 줄 설명 |
|------|-----------|
| Adapter(어댑터) | 호환 안 되는 인터페이스를 **변환(맞춰줌)** |
| Bridge(브리지) | **기능(추상)과 구현을 분리**해 독립적 확장 |
| Composite(컴포지트) | 부분-전체 계층을 **트리 구조**로, 단일/복합 동일 취급 |
| Decorator(데코레이터) | 객체에 **기능을 동적으로 추가**(상속 대신) |
| Facade(퍼사드) | 복잡한 서브시스템에 **단순한 통합 인터페이스** 제공 |
| Flyweight(플라이웨이트) | **공유**로 다수의 유사 객체 메모리 절약 |
| Proxy(프록시) | **대리 객체**로 접근 제어(지연 로딩·보안 등) |

### 행위 패턴 (11) — 객체 간 상호작용/책임
암기: **책·커·인·반·중·메·옵·상·전·템·방**

| 패턴 | 한 줄 설명 |
|------|-----------|
| Chain of Responsibility(책임 연쇄) | 요청을 처리 객체 **사슬로 전달** |
| Command(커맨드) | 요청을 **객체로 캡슐화**(실행·취소·큐잉) |
| Interpreter(인터프리터) | 언어의 **문법을 클래스로** 표현·해석 |
| Iterator(반복자) | 컬렉션 내부구조 노출 없이 **순차 접근** |
| Mediator(중재자) | 객체 간 상호작용을 **중재자에 집중**(결합도↓) |
| Memento(메멘토) | 객체 **상태 저장·복원**(캡슐화 유지, undo) |
| Observer(옵서버) | 상태 변화 시 **의존 객체들에 자동 통지** |
| State(상태) | **상태에 따라 객체 행위** 변경 |
| Strategy(전략) | **알고리즘군을 캡슐화**해 교체 가능하게 |
| Template Method(템플릿 메서드) | 알고리즘 **골격 정의**, 세부는 서브클래스 |
| Visitor(방문자) | 구조 변경 없이 **새 연산(방문)** 추가 |

## 4. 럼바우(Rumbaugh) 객체지향 분석 (OMT) ⭐

`자주 나오는 출제형태:` 3가지 모델링 순서를 쓰시오 / 각 모델링의 다이어그램을 쓰시오.

`핵심 답/암기:` **객체 모델링 → 동적 모델링 → 기능 모델링** (객·동·기)

| 순서 | 모델링 | 내용 / 다이어그램 |
|------|--------|--------------------|
| 1 | 객체(Object) 모델링 | 시스템의 **정적 구조** — 클래스/객체 다이어그램, 속성·관계 표현 |
| 2 | 동적(Dynamic) 모델링 | 시간 흐름에 따른 **상태 변화** — 상태 다이어그램 |
| 3 | 기능(Functional) 모델링 | 데이터 흐름과 **처리 과정** — 자료흐름도(DFD) |

## 5. UML 관계 6종 ⭐

`자주 나오는 출제형태:` 관계명과 표기(화살표)를 연결 / 설명에 맞는 관계를 쓰시오.

`핵심 답/암기:`

| 관계 | 의미 | 표기(화살표) |
|------|------|--------------|
| 연관(Association) | 두 클래스가 **서로 연결**(사용) | 실선 (양방향), 화살표 실선(단방향) |
| 집합/집약(Aggregation) | 전체-부분, **부분이 독립 가능**(약한 소유) | 속이 **빈 마름모** ◇— |
| 포함/합성(Composition) | 전체-부분, **부분이 생명주기 종속**(강한 소유) | 속이 **채워진 마름모** ◆— |
| 일반화(Generalization) | 상속(is-a), 부모-자식 | 속이 **빈 삼각형** ▷ (자식→부모) |
| 의존(Dependency) | 한 클래스가 **일시적으로 사용** | **점선 화살표** ┈▶ |
| 실체화(Realization) | 인터페이스 **구현** | **점선 + 빈 삼각형** ┈▷ |

## 6. UML 다이어그램 분류 ⭐

`자주 나오는 출제형태:` 구조적/행위적으로 분류하시오 / 특정 다이어그램이 어디에 속하는지.

`핵심 답/암기:`

**구조적(정적, Structural) 다이어그램 (6~7)**
- **클래스, 객체, 컴포넌트, 배치(Deployment), 복합체 구조, 패키지**

**행위적(동적, Behavioral) 다이어그램 (7)**
- **유스케이스, 시퀀스, 커뮤니케이션, 상태, 활동, 타이밍, 상호작용 개요**

> 팁: **정적=구조**(클래스/객체/컴포넌트/배치/패키지/복합체), **동적=행위**(유스케이스/시퀀스/상태/활동/타이밍/커뮤니케이션/상호작용개요).
> 시퀀스·커뮤니케이션·타이밍·상호작용개요는 **상호작용(Interaction) 다이어그램**으로 묶임.

## 7. 객체지향(OOP) 핵심 개념 ⭐

`자주 나오는 출제형태:` 설명에 맞는 개념(캡슐화/상속/다형성 등)을 쓰시오 / 오버로딩 vs 오버라이딩 구분.

`핵심 답/암기:`

| 개념 | 설명 |
|------|------|
| 캡슐화(Encapsulation) | 데이터(속성)와 기능(메서드)을 **하나로 묶고** 외부 은닉 |
| 정보 은닉(Information Hiding) | 내부 구현을 **숨기고** 인터페이스로만 접근 (결합도↓) |
| 상속(Inheritance) | 상위 클래스의 속성·메서드를 **하위 클래스가 물려받음** |
| 다형성(Polymorphism) | 같은 메시지에 **객체마다 다르게** 응답 |
| 추상화(Abstraction) | 공통 특성을 뽑아 **모델로 단순화** |

**오버로딩 vs 오버라이딩** (자주 구분 출제)

| 구분 | 오버로딩(Overloading) | 오버라이딩(Overriding) |
|------|----------------------|------------------------|
| 위치 | 같은 클래스 내 | 상속 관계(부모↔자식) |
| 메서드명 | 동일 | 동일 |
| 매개변수 | **다름**(개수·타입) | 동일(시그니처 같음) |
| 개념 | 중복 정의 | **재정의**(덮어쓰기) |

**용어**
- **클래스(Class)**: 객체의 설계도(틀). **인스턴스(Instance)**: 클래스로 생성된 실제 객체. **메시지(Message)**: 객체 간 상호작용(메서드 호출) 요청.

## 8. SOLID 5원칙 ⭐

`자주 나오는 출제형태:` 약어에 해당하는 원칙명을 쓰시오 / 설명에 맞는 원칙.

`핵심 답/암기:`

| 약어 | 원칙 | 내용 |
|------|------|------|
| **SRP** | 단일 책임(Single Responsibility) | 클래스는 **하나의 책임(변경 이유)**만 |
| **OCP** | 개방-폐쇄(Open-Closed) | **확장엔 열림, 변경엔 닫힘** |
| **LSP** | 리스코프 치환(Liskov Substitution) | 자식은 부모를 **완전히 대체** 가능 |
| **ISP** | 인터페이스 분리(Interface Segregation) | 사용 안 하는 인터페이스 **강제 X**(작게 분리) |
| **DIP** | 의존 역전(Dependency Inversion) | 구체가 아닌 **추상(인터페이스)에 의존** |

## 9. 소프트웨어 개발 방법론 ⭐

`자주 나오는 출제형태:` 설명에 맞는 모델명을 쓰시오 / 나선형 모델의 위험분석 / V모델 특징.

`핵심 답/암기:`

| 방법론 | 핵심 |
|--------|------|
| 폭포수(Waterfall) | **순차적·하향식**, 단계 완료 후 다음 진행(고전) |
| 프로토타입(Prototype) | **시제품**을 만들어 요구사항 확인·보완 |
| 나선형(Spiral) | 반복 + **위험 분석(Risk Analysis)** 강조(대규모) — 계획→위험분석→개발→평가 |
| V-모델 | 폭포수 확장, **개발↔테스트 단계 대응**(검증·확인 강조) |
| RAD | 신속한 개발(**4GT·프로토타입** 활용), 짧은 개발 주기 |
| 애자일(Agile) | **반복·점진**, 변화 대응, 고객 협업 |

- **정보공학(Information Engineering)**: 기업 정보시스템을 **체계적·전사적**으로 계획·분석·설계.
- **CBD(Component Based Development)**: 재사용 가능한 **컴포넌트 조립**으로 개발(생산성·재사용성↑).

## 10. 애자일(Agile) ⭐⭐ (최빈출)

`자주 나오는 출제형태:` 애자일 선언 4가치를 쓰시오 / 스크럼 용어 / XP 5가지 가치·실천법.

### 애자일 선언 4가치
1. **공정·도구**보다 **개인·상호작용**
2. **방대한 문서**보다 **작동하는 소프트웨어**
3. **계약 협상**보다 **고객과의 협업**
4. **계획 준수**보다 **변화 대응**

### 스크럼(Scrum)

| 용어 | 설명 |
|------|------|
| 스프린트(Sprint) | 반복 개발 주기(보통 2~4주) |
| 제품 백로그(Product Backlog) | 요구사항 전체 우선순위 목록 |
| 스프린트 백로그(Sprint Backlog) | 해당 스프린트에서 처리할 작업 목록 |
| 번다운 차트(Burn-down Chart) | **남은 작업량**을 시각화(시간↓ 잔여↓) |
| 데일리 스크럼(Daily Scrum) | 매일 짧게(15분) 진행 상황 공유 |
| 스크럼 마스터(Scrum Master) | 팀이 스크럼을 잘 따르도록 지원·장애물 제거 |

### XP(eXtreme Programming)
- **5가지 가치:** 용기(Courage) · 단순성(Simplicity) · 의사소통(Communication) · 피드백(Feedback) · 존중(Respect)
- **실천법(주요):** 페어 프로그래밍(Pair Programming) · **TDD**(테스트 주도 개발) · 리팩토링(Refactoring) · 지속적 통합(CI) · 짧은 릴리즈(Small Releases)

`자주 나오는 출제형태:` 설명에 맞는 아키텍처 패턴을 쓰시오 / MVC 구성요소.

`핵심 답/암기:`

| 패턴 | 설명 |
|------|------|
| 계층화(Layered) | 기능을 **수직 계층**으로 분리(하위 계층이 상위 지원) |

`핵심 답/암기:`

| 미들웨어 | 설명 |

## 13. EAI 구축 유형 ⭐

`자주 나오는 출제형태:` EAI 4가지 구축 유형과 특징 / ESB와의 관계.

`핵심 답/암기:` **Point-to-Point → Hub&Spoke → Message Bus(ESB) → Hybrid**

| 유형 | 설명 |
|------|------|
| Point-to-Point | 애플리케이션 **1:1 직접 연결**(단순, 확장 어려움) |
| Hub & Spoke | **중앙 허브** 경유(관리 편리, 허브 장애 시 전체 영향) |
| Message Bus(ESB) | **버스(미들웨어)** 통해 연계(확장·유연성↑) |
| Hybrid | Hub&Spoke + Message Bus **혼합**(그룹 내 허브, 그룹 간 버스) |

> **EAI(Enterprise Application Integration)** = 기업 내 애플리케이션 통합.
> **ESB(Enterprise Service Bus)** = 서비스(웹서비스) 중심 느슨한 결합의 버스형 통합.

## 14. 요구사항(Requirements) ⭐

`자주 나오는 출제형태:` 기능/비기능 요구사항 구분 / 요구공학 절차를 순서대로.

`핵심 답/암기:`

**요구사항 유형**
- **기능 요구사항(Functional):** 시스템이 **수행해야 할 기능·동작**(무엇을 하는가).
- **비기능 요구사항(Non-functional):** 성능·보안·품질·사용성 등 **제약·품질** 조건.

**요구공학(Requirement Engineering) 절차**
- **도출(Elicitation) → 분석(Analysis) → 명세(Specification) → 확인/검증(Validation)**
- (도출·분석·명세·확인)

**요구사항 명세 기법**
- **정형(Formal):** 수학적 기호·수식으로 명세(Z, VDM 등) — 정확·검증 용이.
- **비정형(Informal):** 자연어·다이어그램 등으로 명세 — 이해 쉬움, 모호성 존재.

## 15. CMMI & SPICE ⭐

`자주 나오는 출제형태:` CMMI 5단계를 순서대로 / SPICE의 표준 번호(ISO/IEC 15504).

`핵심 답/암기:`

**CMMI(능력 성숙도 통합 모델) 5단계**

| 단계 | 이름 | 특징 |
|------|------|------|
| 1 | 초기(Initial) | 무질서·예측 불가 |
| 2 | 관리(Managed) | 프로젝트 단위 관리 |
| 3 | 정의(Defined) | 조직 표준 프로세스 정의 |
| 4 | 정량적 관리(Quantitatively Managed) | 정량적(측정) 관리 |
| 5 | 최적화(Optimizing) | 지속적 개선 |

- **SPICE = ISO/IEC 15504**: 소프트웨어 프로세스 **평가** 국제 표준.
- SPICE 프로세스 수행 능력 6단계: **0 불완전 → 1 수행 → 2 관리 → 3 확립 → 4 예측 → 5 최적화**.

## 16. 소프트웨어 재사용 · 재공학

`자주 나오는 출제형태:` 소프트웨어 재공학 활동을 쓰시오 / 역공학의 개념.

`핵심 답/암기:`

- **재사용(Reuse):** 이미 개발된 SW 자산(코드·설계·문서)을 **재활용**. → 개발 생산성·품질↑.
  - **합성 중심(부품 조립)**, **생성 중심(패턴·명세로 생성)** 접근.
- **재공학(Re-engineering):** 기존 SW를 **분석·재구성**해 유지보수성 향상(예방 유지보수).
  - **재공학 4활동:** **분석(Analysis) → 재구조화(Restructuring) → 역공학(Reverse Eng.) → 이식(Migration)**
- **역공학(Reverse Engineering):** 완성된 SW(코드)를 분석해 **설계·명세 정보**를 추출(개발 반대 방향).
- **정공학(Forward Engineering):** 요구·설계 → 코드(정상 개발 방향).
