# 02. 데이터베이스 · SQL (빈출)

> 정보처리기사 실기(NCS 2020 개정) 대비 단답/서술형 빈출 노트. 프로그래밍 코드 출력 문제 제외, SQL은 구문·개념 위주.
> 표기: ⭐ = 최빈출 / 각 항목은 **개념 → 자주 나오는 출제형태 → 핵심 답·암기** 구성.

## 1. 정규화(Normalization) ⭐ 최빈출

**자주 나오는 출제형태:**
- "각 정규형에서 제거하는 종속(이상)을 순서대로 쓰시오"
- "○○ 종속을 제거한 정규형은?" (역방향 매칭)
- 릴레이션을 주고 "몇 정규형까지 만족하는가"

**핵심 답·암기:** 암기법 **"도부이결다조"** (1→5NF 순서)

| 단계 | 조건 (만족하려면) | 제거 대상 |
|------|------------------|-----------|
| **1NF** | 모든 속성이 **도메인 원자값**(더 쪼갤 수 없는 단일 값)만 가짐 | 반복 그룹·다중 값 제거 |
| **2NF** | 1NF + 기본키에 대한 **완전 함수 종속** (부분 함수 종속 제거) | **부분 함수적 종속** |
| **3NF** | 2NF + **이행적 함수 종속** 없음 (A→B, B→C ⇒ A→C 제거) | **이행적 함수 종속** |
| **BCNF** | 3NF + **모든 결정자(determinant)가 후보키** | 후보키가 아닌 결정자 |
| **4NF** | BCNF + **다치 종속(MVD)** 제거 | 다중값 종속 |
| **5NF** | 4NF + **조인 종속(Join Dependency)** 제거 | 조인 종속 |

- ⭐ 3NF와 BCNF 차이: 3NF는 "이행종속 제거"까지, **BCNF는 결정자가 반드시 후보키**여야 함(3NF보다 강함, "강한 3NF").

## 2. 이상현상(Anomaly)

**개념**: 정규화되지 않은 릴레이션에서 데이터 삽입/삭제/갱신 시 발생하는 부작용. **정규화의 목적 = 이상현상 제거.**

**자주 나오는 출제형태:** "이상현상 3가지를 쓰고 각각 설명하시오"

**핵심 답·암기:**

| 이상현상 | 정의 |
|----------|------|
| **삽입 이상**(Insertion) | 데이터를 삽입할 때 원치 않는 불필요한 값도 함께 삽입해야 하는 현상 (NULL 없이는 삽입 불가) |
| **삭제 이상**(Deletion) | 한 튜플을 삭제할 때 함께 저장된, 유지되어야 할 다른 정보까지 연쇄적으로 삭제되는 현상 |
| **갱신 이상**(Update) | 중복 저장된 값 중 일부만 변경되어 데이터 **불일치(모순)** 가 발생하는 현상 |

---

## 3. 함수적 종속(Functional Dependency, FD)

**개념**: 속성 X의 값이 결정되면 속성 Y의 값이 **유일하게 결정**될 때 "Y는 X에 함수적으로 종속" → 표기 **X → Y** (X: 결정자, Y: 종속자).

**자주 나오는 출제형태:** "부분/완전/이행 함수 종속을 구분·설명하시오"

**핵심 답·암기:**

| 종류 | 정의 |
|------|------|
| **완전 함수 종속** | 기본키 **전체**에 종속 (키의 일부만으로는 결정 불가) → 2NF 목표 |
| **부분 함수 종속** | 기본키의 **일부 속성**에만 종속 (복합키일 때 발생) → 2NF에서 제거 |
| **이행적 함수 종속** | X→Y, Y→Z 이면 X→Z 가 성립 (Z가 X에 간접 종속) → 3NF에서 제거 |

## 4. 키(Key) ⭐

**개념**: 튜플을 유일하게 식별하기 위해 사용하는 속성(집합).

**자주 나오는 출제형태:** "슈퍼키/후보키/기본키 정의", "후보키의 두 가지 특성은?", "외래키 설명"

**핵심 답·암기:** 후보키 특성 = **유일성(Uniqueness) + 최소성(Minimality)**

| 키 | 정의 · 특성 |
|----|------------|
| **슈퍼키**(Super Key) | 튜플을 유일하게 식별하는 속성 집합. **유일성 O, 최소성 X** |
| **후보키**(Candidate Key) | **유일성 + 최소성**을 모두 만족하는 키 (기본키 후보) |
| **기본키**(Primary Key) | 후보키 중 대표로 선정한 키. **NULL 불가, 중복 불가**(유일) |
| **대체키**(Alternate Key) | 후보키 중 기본키로 선택되지 **않은** 나머지 키 (보조키) |
| **외래키**(Foreign Key) | 다른(또는 자기) 릴레이션의 **기본키를 참조**하는 속성. 참조 무결성 담당, NULL 허용 가능 |

- 유일성: 키로 각 튜플을 유일하게 구별. / 최소성: 유일 식별에 꼭 필요한 **최소 속성**만으로 구성.

## 5. 무결성(Integrity) 제약조건

**개념**: 데이터의 정확성·일관성을 보장하기 위한 제약 규칙.

**자주 나오는 출제형태:** ⭐ "개체 무결성과 참조 무결성을 설명하시오", "기본키에 적용되는 무결성은?"

**핵심 답·암기:**

| 무결성 | 규칙 |
|--------|------|
| **개체 무결성**(Entity) | 기본키를 구성하는 속성은 **NULL 값이나 중복값을 가질 수 없다** (유일·NOT NULL) |
| **참조 무결성**(Referential) | 외래키 값은 참조하는 릴레이션의 **기본키 값과 일치하거나 NULL**이어야 한다 |
| **도메인 무결성**(Domain) | 속성값은 정의된 **도메인(자료형·범위·형식)**에 속하는 값이어야 한다 |
| **사용자 정의 무결성**(User-defined) | 업무 규칙에 따라 사용자가 정의한 제약조건을 만족해야 한다 |

## 6. 트랜잭션(Transaction) · ACID ⭐

**개념**: 데이터베이스의 상태를 변화시키는 **하나의 논리적 작업 단위**. 더 이상 분해할 수 없는 연산의 집합.

**자주 나오는 출제형태:** ⭐ "트랜잭션의 특성(ACID) 4가지를 쓰고 설명", "원자성을 보장하는 SQL 명령은?"

**핵심 답·암기:** **ACID**

| 특성 | 정의 |
|------|------|
| **원자성**(Atomicity) | 트랜잭션의 연산은 **모두 반영되거나 모두 반영되지 않아야**(All or Nothing) 한다 |
| **일관성**(Consistency) | 트랜잭션 수행 전과 후의 데이터베이스가 **일관된(모순 없는) 상태**를 유지 |
| **격리성**(Isolation) | 수행 중인 트랜잭션의 연산에 다른 트랜잭션이 **끼어들 수 없음**(고립성) |
| **지속성**(Durability) | 성공적으로 **완료(COMMIT)된 트랜잭션 결과는 영구적으로 반영** |

**트랜잭션 제어(TCL) 명령:**

| 명령 | 용도 |
|------|------|
| **COMMIT** | 트랜잭션의 변경 내용을 DB에 **영구 저장(확정)** |
| **ROLLBACK** | 변경 내용을 취소하고 이전 상태(마지막 COMMIT 시점)로 **되돌림** |
| **SAVEPOINT** | 트랜잭션 내 **저장점** 설정 → `ROLLBACK TO 저장점`으로 일부만 취소 가능 |

## 7. 트랜잭션 격리 수준(Isolation Level)

**개념**: 동시 트랜잭션이 서로에게 영향을 주는 정도를 조절하는 단계. 낮을수록 동시성↑·일관성↓, 높을수록 반대.

**자주 나오는 출제형태:** "격리 수준 4단계", "Dirty Read를 방지하는 최소 격리 수준은?"

**핵심 답·암기:**

| 격리 수준 (낮음→높음) | 허용되는 이상현상 |
|----------------------|------------------|
| **Read Uncommitted** | Dirty Read, Non-repeatable Read, Phantom Read 모두 발생 가능 |
| **Read Committed** | Dirty Read 방지 (Non-repeatable·Phantom 발생 가능) |
| **Repeatable Read** | Dirty·Non-repeatable Read 방지 (Phantom 발생 가능) |
| **Serializable** | 모든 이상현상 방지 (완전 직렬화, 동시성 가장 낮음) |

**동시성 이상현상:**

| 현상 | 정의 |
|------|------|
| **Dirty Read** | 아직 **COMMIT되지 않은**(변경 중인) 데이터를 다른 트랜잭션이 읽음 |
| **Non-repeatable Read** | 한 트랜잭션이 같은 행을 두 번 읽을 때, 사이에 **수정/삭제**되어 값이 달라짐 |
| **Phantom Read** | 같은 조건으로 두 번 조회 시, 사이에 **삽입**된 행(유령 행)이 나타남 |

## 8. 병행 제어(Concurrency Control)

**개념**: 여러 트랜잭션이 동시에 실행될 때 상호 간섭을 제어하여 **일관성**을 유지하는 기법.

**자주 나오는 출제형태:** "병행 제어 기법을 나열", "2단계 로킹의 두 단계는?", "교착상태 정의"

**핵심 답·암기:**

| 기법 | 설명 |
|------|------|
| **로킹**(Locking) | 트랜잭션이 접근할 데이터에 **잠금(Lock)** 을 걸어 다른 트랜잭션 접근 차단. 공유락(S)·배타락(X) |
| **2단계 로킹**(2PL) | **확장 단계**(Lock만 획득) → **수축 단계**(Unlock만 수행). 직렬성 보장, **교착상태는 못 막음** |
| **타임스탬프 순서**(Timestamp Ordering) | 트랜잭션에 **시간표(고유 순번)** 를 부여해 그 순서대로 처리 → 교착상태 없음 |
| **낙관적 검증**(Optimistic / Validation) | 일단 수행하고 **커밋 직전 검증**, 충돌 시 롤백 (충돌이 드물다고 가정) |

- **교착상태(Deadlock)**: 둘 이상의 트랜잭션이 서로 상대가 점유한 자원의 락 해제를 무한정 기다려 **아무도 진행 못 하는 상태**.
  - 4대 필요조건: **상호배제 · 점유와 대기 · 비선점 · 환형(순환) 대기**.
  - 해결: 예방(Prevention)·회피(Avoidance, 은행원 알고리즘)·탐지(Detection)·회복(Recovery).

| **외부 스키마**(External) | 개별 사용자·응용 프로그램 관점 (서브스키마, **뷰**). 여러 개 존재 |
| **개념 스키마**(Conceptual) | 조직 전체의 통합된 관점. **DB당 하나만** 존재 |
| **내부 스키마**(Internal) | 물리적 저장장치 관점 (저장구조·인덱스·레코드 형식) |

- **논리적 데이터 독립성**: 개념 스키마 변경 시 외부 스키마·응용 프로그램에 영향 없음.
- **물리적 데이터 독립성**: 내부 스키마(저장구조) 변경 시 개념 스키마에 영향 없음.

## 10. 관계 대수(절차적) vs 관계 해석(비절차적)

**개념**: 관계형 DB의 질의를 표현하는 이론적 언어.
- **관계 대수**: "**어떻게(How)** 데이터를 얻는가"를 명시하는 **절차적** 언어.
- **관계 해석**: "**무엇(What)** 을 얻을지"만 명시하는 **비절차적** 언어(수학의 **술어 논리** 기반).

**자주 나오는 출제형태:** ⭐ "순수 관계 연산자 4가지와 기호", "관계 대수와 관계 해석 차이"

**핵심 답·암기:**

**① 순수 관계 연산자** (관계 DB 전용)

| 연산 | 기호 | 의미 |
|------|------|------|
| **Select** | **σ** (시그마) | 조건을 만족하는 **행(튜플)** 선택 (수평) |
| **Project** | **π** (파이) | 지정한 **열(속성)** 선택 (수직, 중복 제거) |
| **Join** | **⋈** (bowtie) | 공통 속성으로 두 릴레이션을 연결 |
| **Division** | **÷** | R의 튜플 중 S의 모든 값과 대응되는 튜플 추출 |

**② 일반 집합 연산자** (수학 집합 연산)

| 연산 | 기호 |
|------|------|
| **합집합**(Union) | ∪ |
| **교집합**(Intersection) | ∩ |
| **차집합**(Difference) | − |
| **카티션 곱**(Cartesian Product) | × |

**③ 관계 해석**: 튜플 관계 해석 / 도메인 관계 해석으로 구분. 술어 논리(정량자 ∀, ∃) 사용, 비절차적.

## 11. 반정규화(De-normalization)

**개념**: 정규화된 DB에서 **성능(조회 속도) 향상**을 위해 의도적으로 중복을 허용하거나 테이블을 통합·분할하는 기법. (정규화의 반대 → 무결성↓, 성능↑)

**자주 나오는 출제형태:** "반정규화 정의와 기법", "정규화와 반정규화 목적 비교"

**핵심 답·암기:**

| 기법 | 설명 |
|------|------|
| **테이블 통합** | 자주 함께 조회되는 테이블을 하나로 합침 (조인 감소) |
| **테이블 분할** | 수평 분할(행 기준)·수직 분할(열 기준)로 나눔 |
| **중복 컬럼 추가** | 조인을 피하기 위해 다른 테이블의 컬럼을 복제 |
| **파생 컬럼 추가** | 계산 결과(합계 등)를 미리 저장 |
| **이력 테이블 추가** | 반복 조회되는 이력을 별도 테이블로 관리 |

## 12. E-R 다이어그램(개체-관계 모델)

**개념**: 현실 세계를 **개체(Entity)-관계(Relationship)** 로 표현하는 개념적 데이터 모델(피터 첸 제안).

**자주 나오는 출제형태:** ⭐ "E-R 다이어그램 기호(개체·속성·관계)를 매칭", "카디널리티 종류"

**핵심 답·암기:**

| 요소 | 기호 |
|------|------|
| **개체**(Entity) | **사각형 □** |
| **속성**(Attribute) | **타원 ○** |
| **관계**(Relationship) | **마름모 ◇** |
| **연결**(Link) | **선 —** (개체·속성·관계를 연결) |
| 기본키 속성 | 밑줄 친 타원 |

- **카디널리티(Cardinality, 대응 수)**: **1:1**(일대일) · **1:N**(일대다) · **N:M**(다대다).

## 13. SQL 분류 ⭐ (DDL / DML / DCL)

**개념**: SQL 명령을 기능에 따라 3(~4)종으로 분류.

**자주 나오는 출제형태:** ⭐ "다음 명령을 DDL/DML/DCL로 분류하시오", "TRUNCATE는 어디에 속하는가"

**핵심 답·암기:**

| 분류 | 명령 | 용도 |
|------|------|------|
| **DDL** (데이터 정의어) | **CREATE** | 테이블·뷰·인덱스 등 객체 **생성** |
| | **ALTER** | 객체 구조 **변경**(컬럼 추가/수정) |
| | **DROP** | 객체 **삭제**(정의 자체 제거) |
| | **TRUNCATE** | 테이블의 **모든 행 삭제**(구조 유지, 롤백 어려움) |
| **DML** (데이터 조작어) | **SELECT** | 데이터 **검색(조회)** |
| | **INSERT** | 데이터 **삽입** |
| | **UPDATE** | 데이터 **수정** |
| | **DELETE** | 데이터 **삭제**(행 단위) |
| **DCL** (데이터 제어어) | **GRANT** | 권한 **부여** |
| | **REVOKE** | 권한 **회수** |
| | **COMMIT** / **ROLLBACK** | 트랜잭션 확정/취소 (TCL로 분리하기도 함) |

- 팁: DELETE(DML, 행 단위·조건 가능·롤백 가능) vs **TRUNCATE(DDL, 전체·빠름·구조 유지)** vs **DROP(DDL, 객체 자체 제거)** 비교 빈출.

## 14. SQL 빈출 구문 ⭐

**개념**: SELECT 문의 절(clause)과 조인·서브쿼리·집계함수 등 핵심 구문.

**자주 나오는 출제형태:** ⭐ "다음 요구사항에 맞는 SQL을 완성하시오"(빈칸), "GROUP BY / HAVING 차이", "WHERE와 HAVING 차이"

**핵심 답·암기:**

**① SELECT 절 순서와 실행 개념**

```sql
SELECT   컬럼, 집계함수      -- 5. 표시할 열 선택
FROM     테이블              -- 1. 대상 테이블
WHERE    행_조건             -- 2. 행 필터 (그룹화 前, 집계함수 사용 불가)
GROUP BY 그룹기준_컬럼        -- 3. 지정 컬럼으로 그룹화
HAVING   그룹_조건           -- 4. 그룹 필터 (집계함수 조건 가능)
ORDER BY 정렬컬럼 [ASC|DESC];-- 6. 정렬 (기본 ASC)
```

- 작성 순서: `SELECT–FROM–WHERE–GROUP BY–HAVING–ORDER BY`
- 실제 처리(개념) 순서: **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY**
- ⭐ **WHERE = 행 조건(그룹화 전)** / **HAVING = 그룹 조건(집계함수 조건, 그룹화 후)**.

**② 집계(집단) 함수**

| 함수 | 기능 |
|------|------|
| **COUNT** | 행 개수 |
| **SUM** | 합계 |
| **AVG** | 평균 |
| **MAX / MIN** | 최댓값 / 최솟값 |

**③ 조건 연산자**: `LIKE`(패턴, `%`=0글자 이상·`_`=1글자), `IN(값,…)`(목록 일치), `BETWEEN a AND b`(범위, 양끝 포함), `DISTINCT`(중복 제거).

**④ JOIN**

| 조인 | 결과 |
|------|------|
| **INNER JOIN** | 양쪽 테이블에 **모두 존재**하는 매칭 행만 |
| **LEFT OUTER JOIN** | 왼쪽 전부 + 매칭되는 오른쪽 (없으면 NULL) |
| **RIGHT OUTER JOIN** | 오른쪽 전부 + 매칭되는 왼쪽 |
| **FULL OUTER JOIN** | 양쪽 전부 (매칭 없으면 NULL) |

**⑤ 예제 SQL**

```sql
-- 부서별 인원수가 3명 이상인 부서의 평균 급여를 급여 내림차순으로 조회
SELECT   부서, COUNT(*) AS 인원, AVG(급여) AS 평균급여
FROM     사원
WHERE    입사연도 >= 2020          -- 행 필터
GROUP BY 부서                       -- 부서별 그룹화
HAVING   COUNT(*) >= 3              -- 그룹 필터(집계 조건)
ORDER BY 평균급여 DESC;             -- 정렬
```

```sql
-- 서브쿼리: 평균 급여보다 많이 받는 사원
SELECT 이름, 급여
FROM   사원
WHERE  급여 > (SELECT AVG(급여) FROM 사원);
```

**⑥ GRANT / REVOKE 예시**

```sql
GRANT  SELECT, UPDATE ON 사원 TO 홍길동 WITH GRANT OPTION;  -- 권한 부여(+재부여 권한)
REVOKE SELECT, UPDATE ON 사원 FROM 홍길동;                   -- 권한 회수
```

- `WITH GRANT OPTION`: 부여받은 권한을 **다른 사용자에게 다시 부여**할 수 있는 권한.

## 15. 뷰(View) · 인덱스(Index)

### 뷰(View)

**개념**: 하나 이상의 기본 테이블로부터 유도된 **가상 테이블**. 물리적 데이터는 없고 정의(SELECT)만 저장.

**자주 나오는 출제형태:** "뷰의 정의와 장단점", "뷰를 생성/삭제하는 SQL"

**핵심 답·암기:**

| 장점 | 단점 |
|------|------|
| 논리적 독립성 제공 | 정의 변경 불가(**변경하려면 DROP 후 재생성**) |
| 필요한 데이터만 노출 → **보안** | 삽입·수정·삭제 연산에 **제약** |
| 질의 단순화 | 인덱스를 가질 수 없음 |

```sql
CREATE VIEW 우수사원 AS
  SELECT 이름, 급여 FROM 사원 WHERE 급여 >= 5000;
DROP VIEW 우수사원;
```

### 인덱스(Index)

**개념**: 데이터 **검색 속도 향상**을 위해 컬럼 값과 저장 위치를 별도로 관리하는 자료구조(주로 B-tree).

**자주 나오는 출제형태:** "인덱스의 목적과 단점", "인덱스 생성 SQL"

**핵심 답·암기:**

| 장점 | 단점 |
|------|------|
| **SELECT(검색) 성능 향상** | INSERT·UPDATE·DELETE 시 인덱스도 갱신 → **성능 저하** |
| 정렬·범위 조회 효율↑ | 추가 **저장 공간** 필요 |

```sql
CREATE INDEX idx_사원_이름 ON 사원(이름);
DROP INDEX idx_사원_이름;
```

## 16. 데이터 모델링 절차 (개념 → 논리 → 물리)

**개념**: 현실 데이터를 DB로 구현하기까지의 단계적 설계 과정.

**자주 나오는 출제형태:** "데이터 모델링 3단계를 순서대로 쓰시오"

**핵심 답·암기:**

| 단계 | 산출물 · 활동 |
|------|--------------|
| **개념적 모델링** | 업무 중심 개체·관계 도출 → **E-R 다이어그램** (DBMS 독립적) |
| **논리적 모델링** | 개념 모델을 특정 데이터 모델(관계형 등)로 변환 → **정규화**, 테이블·키 정의 |
| **물리적 모델링** | 실제 DBMS에 맞게 저장구조·**인덱스**·성능(반정규화) 설계 → 물리 스키마 |

- 데이터 모델의 3요소: **구조(Structure) · 연산(Operation) · 제약조건(Constraint)**.

> 학습 팁: ⭐ 표시(정규화·ACID·스키마 3층·순수 관계 연산·SQL 분류·SELECT 구문)는 매 회차 단골 출제. 정의는 **키워드 위주로 암기**하고 서술형은 "무엇을 제거/보장하는가"를 문장으로 쓸 수 있게 연습.
