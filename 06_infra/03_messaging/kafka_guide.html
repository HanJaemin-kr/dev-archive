Overview
Kafka의 본질 = 분산 커밋 로그
카프카의 모든 특징(고처리량·재처리·순서보장·내결함성)은 "메시지를 디스크에 순차적으로 append하는 로그"라는 단 하나의 설계에서 파생됩니다.

📜 Append-only Log

메시지를 수정/삭제하지 않고 파일 끝에 계속 이어 붙임. 각 메시지엔 순번(offset)이 매겨짐. 읽기는 offset 위치부터 순서대로.

💾 순차 디스크 I/O

랜덤 I/O가 아니라 순차 쓰기/읽기 → HDD에서도 초당 수백 MB. "디스크는 느리다"는 통념을 순차 접근으로 깸.

🗂️ OS Page Cache 활용

JVM 힙 대신 OS 페이지 캐시에 데이터를 둠. 최근 쓴 데이터를 컨슈머가 곧 읽으면 디스크까지 안 감(캐시 히트).

🚀 Zero-Copy 전송

sendfile()로 페이지 캐시 → 소켓 직행. 유저 공간 복사·직렬화 없이 파일을 그대로 네트워크로.

📦 배치 + 압축

메시지를 낱개가 아니라 batch로 묶어 전송·저장·복제. 네트워크 왕복과 디스크 쓰기 횟수를 줄임.

🔀 파티션 병렬성

토픽을 여러 파티션으로 쪼개 브로커·컨슈머에 분산. 처리량이 파티션 수에 따라 수평 확장.

핵심 관점: "큐에서 메시지를 꺼내면 사라진다"가 아니라, "로그의 어디까지 읽었는지(offset)만 컨슈머가 기억"합니다. 데이터는 보존 기간 동안 그대로 남아 여러 컨슈머가 각자 다른 위치를 읽습니다.
Architecture
클러스터 전체 구조
브로커 여러 대가 클러스터를 이루고, 각 파티션은 한 브로커가 Leader, 나머지가 Follower(복제본)를 맡습니다. 메타데이터는 Controller가 관리합니다.
클러스터 구조 — 파티션별 Leader가 브로커에 분산되고, Follower가 복제하며, Controller가 메타데이터를 관리
구성 요소역할내부 포인트
Broker메시지 저장·전송을 담당하는 서버 1대파티션의 Leader/Follower 복제본을 로컬 디스크에 보관
Partition토픽을 물리적으로 나눈 로그 단위순서 보장·병렬성의 최소 단위. 디스크의 한 디렉토리
Leader Replica해당 파티션의 모든 읽기/쓰기 처리Producer·Consumer는 Leader하고만 통신
Follower ReplicaLeader를 복제(fetch)해 장애 대비ISR에 속해야 Leader 승격 자격
ControllerLeader 선출·ISR 관리·메타데이터KRaft에선 Raft 쿼럼, 과거엔 ZooKeeper
Storage
저장 구조 — Partition → Segment → 파일
파티션 하나는 디스크의 디렉토리이고, 그 안은 여러 세그먼트(segment) 파일로 쪼개집니다. 각 세그먼트는 .log(실데이터) + .index(오프셋→위치) + .timeindex(시간→오프셋) 세트로 구성됩니다.
파티션 = 디렉토리, 세그먼트 = 파일 세트. 쓰기는 active segment 끝에만, 삭제는 오래된 세그먼트 통째로

Sparse Index — offset으로 위치를 어떻게 찾나

모든 메시지를 인덱싱하면 인덱스가 너무 커지므로, 카프카는 일정 간격(기본 4KB)마다 하나씩만 기록하는 sparse index를 씁니다. 원하는 offset의 가장 가까운 이전 인덱스 항목으로 점프한 뒤, 거기서부터 .log를 순차 스캔합니다.

Sparse index로 대략 위치까지 점프 후 짧게 순차 스캔 — 인덱스 크기와 조회 속도의 균형
Record Format
레코드 배치 포맷 (on-disk / on-wire)
카프카는 메시지를 낱개가 아니라 Record Batch 단위로 저장·전송합니다(v2 포맷, Kafka 0.11+). Producer가 만든 배치가 그대로 디스크에 쓰이고 컨슈머에게 그대로 전달됩니다 → 재압축·재직렬화 불필요.
offsetDelta keyLength · key · valueLength · value headers[] (사용자 정의 K/V) Record #1 … 실제 offset = baseOffset + offsetDelta 실제 ts = baseTimestamp + timestampDelta → delta 저장으로 공간 절약(가변길이 varint)
배치 헤더는 한 번만, 개별 레코드는 delta로 압축 저장 — 오프셋/타임스탬프는 base+delta로 복원
왜 이렇게? ① 공통 메타를 배치당 1회만 저장(공간↓) ② 압축을 배치 단위로 적용(압축률↑) ③ Producer가 압축·직렬화한 배치를 브로커가 그대로 저장하고 Consumer에게 그대로 전달 → 브로커 CPU 절약 + zero-copy 가능.
Producer
프로듀서 내부 동작
send()는 즉시 전송이 아니라 버퍼에 쌓는 것입니다. 별도 Sender 스레드가 파티션별로 배치를 모아 브로커로 보냅니다.
send()는 버퍼링 → Sender 스레드가 batch.size / linger.ms 조건으로 묶어 전송
acks — 쓰기 확인 수준
acks의미트레이드오프
0보내고 끝(확인 X)유실 가능·최고 속도
1Leader만 기록 확인Leader 죽으면 유실 가능
allISR 전체 기록 확인유실 없음·상대적 느림
멱등성 & 순서 (idempotent producer)
enable.idempotence=true → Producer마다 PID + 파티션별 시퀀스 번호를 붙임.
브로커가 seq를 검사해 재시도로 인한 중복을 제거하고 순서를 보장.
acks=all + max.in.flight≤5와 함께 exactly-once의 토대.
Replication
복제 · ISR · High Watermark
Follower는 Leader에게서 데이터를 fetch해 복제합니다. 충분히 따라잡은 복제본 집합이 ISR(In-Sync Replicas), 컨슈머가 볼 수 있는 안전한 경계선이 High Watermark(HW)입니다.
모두가 복제 완료한 offset. 컨슈머는 HW 미만까지만 읽을 수 있음(=committed) HW~LEO 구간 (여기선 4~5) 아직 복제 안 끝난 uncommitted. 컨슈머에게 안 보임 → Leader 장애 시 유실돼도 안전 ISR Leader를 제 시간에 따라잡은 복제본 집합. acks=all은 ISR 전원 기록을 기다림 min.insync.replicas=2 → ISR<2면 acks=all 쓰기 거부(가용성보다 안전 택함)
컨슈머는 HW까지만 읽음 → 복제 안 끝난 데이터는 노출 안 됨. ISR·min.insync.replicas가 유실 방지의 핵심
Leader 장애 시나리오: Controller가 ISR 중 하나를 새 Leader로 승격. ISR 밖 복제본이 승격되면(unclean.leader.election=true) 데이터 유실 가능 → 운영에선 보통 false로 안전 우선.
Read Path
읽기 경로 & Zero-Copy
컨슈머의 fetch 요청에 대해, 브로커는 파일 데이터를 유저 공간으로 복사하지 않고 sendfile()로 페이지 캐시에서 소켓으로 직접 보냅니다.
Zero-copy는 브로커가 배치를 "그대로 전달"하기에 가능 — 카프카 고처리량의 핵심 메커니즘
Consumer
컨슈머 그룹 · 리밸런싱 · 오프셋
한 그룹 안에서 파티션은 컨슈머에게 겹치지 않게 배정됩니다. 멤버 변화가 생기면 Group Coordinator가 재배정(rebalance)합니다. 각자 어디까지 읽었는지는 내부 토픽 __consumer_offsets에 저장됩니다.
그룹 내 파티션은 배타적 배정 · Coordinator가 리밸런싱 · offset은 __consumer_offsets에 커밋
offset 커밋 = "여기까지 처리했다" 표시
커밋된 offset은 다음에 읽을 위치. 재시작하면 그 지점부터 이어 읽음.
auto commit: 주기적 자동(간단하나 중복/유실 창 존재).
manual commit: 처리 성공 후 커밋 → at-least-once 보장.
중복 vs 유실은 커밋 시점이 결정
처리 전 커밋 → 장애 시 유실(at-most-once).
처리 후 커밋 → 장애 시 재처리(at-least-once, 멱등 처리 필요).
static membership(group.instance.id)으로 재시작 리밸런싱 회피 가능.
Controller
메타데이터 관리 — KRaft vs ZooKeeper
"어느 파티션의 Leader가 누구인지, ISR은 무엇인지" 같은 클러스터 메타데이터를 누가 관리하느냐의 문제. 과거엔 외부 ZooKeeper, 지금은 카프카 내장 KRaft(Raft 합의)입니다.
KRaft는 메타데이터마저 복제 로그로 관리 — 외부 ZooKeeper 없이 확장성·복구속도 개선
Retention
보존 정책 & 로그 컴팩션
오래된 데이터를 정리하는 두 방식: delete(시간/크기 초과분 삭제) vs compact(키별 최신값만 남김).
세그먼트 통째 삭제. 일반 스트림 데이터용. 예: 진동 원시데이터 3일 보존 후 삭제 cleanup.policy=compact 키별 최신값 유지 → "현재 상태" 저장소. changelog·설정·KTable용. 예: 설비별 최신 설정, 컨슈머 오프셋 토픽
delete는 오래된 것 삭제, compact는 키별 최신값만 보존 — __consumer_offsets도 compact 토픽
Delivery
전달 보장 (Delivery Semantics)
내부 메커니즘(멱등 producer·offset 커밋 시점·트랜잭션)이 조합되어 세 가지 보장 수준을 만듭니다.
수준의미구성 방법비고
At most once유실 가능, 중복 없음acks=0/1, 처리 전 offset 커밋속도 우선(고주파 센서)
At least once유실 없음, 중복 가능acks=all, 처리 후 커밋가장 일반적, 멱등 처리 전제
Exactly once유실·중복 없음멱등 producer + 트랜잭션(read-process-write)EOS. Kafka Streams 기본
Exactly-once(EOS) 핵심: ① 멱등 producer(PID+seq)로 재시도 중복 제거 → ② 트랜잭션으로 "여러 파티션 쓰기 + offset 커밋"을 원자적으로 묶음 → ③ 컨슈머는 isolation.level=read_committed로 커밋된 트랜잭션만 읽음. 이 조합이 "정확히 한 번" 파이프라인을 만듭니다.
⚙️ 유실 없는 운영 설정 예시 (server / producer)
# Broker/Topic
replication.factor = 3
min.insync.replicas = 2          # ISR 2 미만이면 acks=all 쓰기 거부
unclean.leader.election.enable = false

# Producer
acks = all
enable.idempotence = true        # PID+seq → 중복 제거·순서 보장
max.in.flight.requests.per.connection = 5
retries = 2147483647             # 사실상 무한 재시도(멱등이라 안전)

# Consumer
enable.auto.commit = false       # 처리 후 수동 커밋 → at-least-once
isolation.level = read_committed # 트랜잭션 EOS 시
Interview
면접 Q&A
Q. Kafka가 디스크를 쓰는데도 빠른 이유는?
append-only 순차 I/O(랜덤 X) + OS 페이지 캐시 활용 + zero-copy(sendfile) + 배치·압축. 즉 "디스크가 느린 게 아니라 랜덤 접근이 느린 것"을 순차 로그 구조로 회피.
Q. High Watermark와 LEO의 차이는?
LEO는 복제본이 마지막으로 쓴 다음 offset(로컬 끝). HW는 ISR 전부가 복제 완료한 offset. 컨슈머는 HW까지만 읽음 → 복제 안 끝난 데이터가 노출되지 않아 Leader 장애 시에도 안전.
Q. 파티션 안에서만 순서가 보장되는 이유는?
offset은 파티션별로 매겨지고, 쓰기는 Leader의 로그 끝에 순차 append되기 때문. 토픽 전체 순서는 보장 안 됨 → 순서가 필요한 데이터는 같은 key로 같은 파티션에 보내야 함.
Q. acks=all이면 무조건 유실이 없나?
아니오. min.insync.replicas가 함께 있어야 함. ISR이 1개로 줄어든 상태에서 acks=all은 그 1개만 확인하므로, 그 브로커가 죽으면 유실. 그래서 replication.factor=3 + min.insync.replicas=2 조합을 씀.
Q. 컨슈머를 파티션 수보다 많이 두면?
초과 컨슈머는 놀게 됨(idle). 한 파티션은 그룹 내 한 컨슈머만 소비하므로 병렬성의 상한은 파티션 수. 확장 계획이 있으면 파티션을 넉넉히 잡아야 함.
Q. 리밸런싱이 왜 문제이고, 어떻게 줄이나?
eager 방식은 전원이 멈추고 재배정하는 stop-the-world라 지연 발생. cooperative(incremental) 리밸런싱으로 바뀌는 파티션만 넘기고, static membership(group.instance.id)으로 재시작 시 불필요한 리밸런싱을 회피.
Q. Log compaction은 언제 쓰나?
"현재 상태"만 필요할 때. 키별 최신값만 남기므로 changelog, 설비 최신 설정, KTable, __consumer_offsets 같은 상태 저장에 적합. 이력이 필요하면 delete 정책 + 긴 보존.
Q. KRaft가 ZooKeeper보다 나은 점은?
외부 시스템 의존 제거(운영 단순), 메타데이터를 복제 로그로 관리해 수백만 파티션까지 확장, 컨트롤러 장애복구가 훨씬 빠름. 메타데이터 전파도 로그 구독 방식이라 일관적.
Q. Exactly-once는 실제로 어떻게 달성되나?
멱등 producer(PID+시퀀스)로 재전송 중복 제거 + 트랜잭션으로 "메시지 쓰기 + offset 커밋"을 원자적으로 묶음 + 컨슈머 read_committed. 이 3요소 조합. Kafka Streams는 이를 기본 제공(processing.guarantee=exactly_once_v2).
