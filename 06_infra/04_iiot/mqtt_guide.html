Overview
MQTT란?
1999년 IBM에서 원유 파이프라인 모니터링을 위해 설계. 2014년 OASIS 표준, 2016년 ISO/IEC 20922 국제 표준 채택.

🪶 초경량 프로토콜

헤더가 최소 2 byte. 저대역폭(2G·위성)·저전력 환경(MCU)에서도 안정 동작. REST/HTTP 대비 10배 이상 효율.

📡 발행-구독 모델

Publisher와 Subscriber가 직접 연결하지 않음. Broker가 중간에서 메시지를 라우팅. 완전한 디커플링.

🔗 비동기 통신

Publisher는 Subscriber의 존재를 모름. Subscriber는 Publisher를 알 필요 없음. 시간·공간적으로 독립.

📊 QoS 3단계

At most once(0) / At least once(1) / Exactly once(2). 네트워크 신뢰성에 따라 선택적 적용.

📌 Retain 메시지

브로커가 토픽의 마지막 메시지를 저장. 새 구독자가 연결되면 즉시 최신값 수신. 실시간 상태 공유에 핵심.

🪦 Last Will

클라이언트가 비정상 종료 시 브로커가 대신 발행하는 메시지. 장비 오프라인 감지에 필수.

MQTT Pub/Sub 아키텍처 — 브로커 중심의 완전한 디커플링 구조

핵심 개념

Broker모든 메시지가 거치는 중앙 서버. 토픽 매칭, QoS 관리, Retain·Will 처리 담당Mosquitto, EMQX, HiveMQ, AWS IoT Core

Topic메시지를 분류하는 UTF-8 계층 경로. 구분자: /pdm/line1/pump01/vibration
Payload실제 데이터. 바이너리·JSON·텍스트 등 형식 자유 (브로커는 내용을 해석하지 않음){"value":3.14,"ts":"..."}
QoS메시지 전달 보증 수준. 0·1·2 세 단계0=Fire-and-forget, 1=At least once, 2=Exactly once
Retain브로커가 토픽의 마지막 메시지를 저장. 새 구독자가 연결 즉시 수신상태 공유, 설정값 배포에 핵심
Last Will (LWT)클라이언트가 비정상 종료 시 브로커가 대신 특정 토픽에 발행하는 메시지devices/pump01/status = offline
Keep-Alive클라이언트가 일정 주기로 PINGREQ 전송. 브로커가 응답 없으면 연결 종료 처리기본값 60초. LWT 트리거 조건
Clean Sessiontrue: 재접속 시 구독 정보·미전달 메시지 초기화. false: 오프라인 중 메시지 유지(QoS 1·2)False = Persistent Session

QoS
QoS (Quality of Service)
메시지 전달 보증 수준. Publisher→Broker, Broker→Subscriber 각각 독립적으로 설정됩니다.
0
At Most Once
최대 1회 전달
확인 없음
▸ 네트워크 오버헤드 최소
▸ 손실 허용 데이터 (로그)
▸ 고주파 센서 데이터
▸ 재전송 없음
1
At Least Once
최소 1회 전달
PUBACK 확인
▸ 중복 가능성 있음
▸ 멱등성 처리 필요
▸ 일반적 IoT 사용
▸ 가장 널리 사용
2
Exactly Once
정확히 1회 전달
4단계 핸드셰이크
▸ 중복·손실 없음
▸ 제어 명령·결제
▸ 오버헤드 가장 큼
▸ 4-way 핸드셰이크
QoS별 메시지 교환 횟수 — QoS가 높을수록 신뢰성↑, 오버헤드↑
실무 선택 기준
진동·온도 고주파 데이터 → QoS 0 (손실 일부 허용, 성능 우선)
일반 센서 로깅, 상태 업데이트 → QoS 1 (멱등성 처리 전제, 가장 일반적)
제어 명령, 설정 변경 → QoS 2 (정확한 1회 실행 필수)

Security
보안
MQTT 자체에는 보안이 없음 — TLS, 인증, 권한 제어를 별도로 구성해야 합니다.

🔒 TLS/SSL 암호화

포트 8883에서 TLS 연결. CONNECT 패킷 포함 모든 메시지 암호화. 도청 방지.

🔑 Username/Password

CONNECT 패킷에 자격증명 포함. 반드시 TLS와 함께 사용 (평문 위험).

📜 X.509 인증서

클라이언트 인증서로 상호 TLS(mTLS). Username/Password 없이 인증서로 인증.

🚦 ACL (접근 제어)

클라이언트별 발행/구독 가능 토픽 제한. 브로커 설정 파일 또는 플러그인으로 구성.

🛡️ IP 화이트리스트

신뢰된 IP만 브로커 접속 허용. 방화벽과 조합해 네트워크 레벨 방어.

🔍 MQTT 5.0 Enhanced Auth

SASL·OAuth 2.0 등 확장 인증 메커니즘 지원. CHALLENGE-RESPONSE 방식.

🔐 TLS + ACL 설정 예시 (mosquitto.conf)
# TLS 리스너
listener 8883
cafile   /mosquitto/certs/ca.crt
certfile /mosquitto/certs/server.crt
keyfile  /mosquitto/certs/server.key
require_certificate true   # 클라이언트 인증서 필수 (mTLS)
tls_version tlsv1.3

# 인증 파일 (비밀번호)
password_file /mosquitto/passwd

# ACL 파일
acl_file /mosquitto/acl

# acl 파일 내용 예시:
# user collector_01
# topic read  pdm/#
# topic write pdm/line1/pump01/#
#
# user dashboard
# topic read  pdm/#
주의: 개발 환경에서 allow_anonymous true를 사용했다면 운영 배포 전 반드시 allow_anonymous false로 변경 + TLS + ACL 구성 필요. 기본 포트 1883은 평문이므로 운영에서 절대 사용 금지.

📤 Publisher (paho-mqtt)
import json, time
import paho.mqtt.client as mqtt

BROKER = "localhost"
PORT   = 1883

def on_connect(client, userdata, flags, rc):
    print(f"Connected rc={rc}")

client = mqtt.Client(client_id="collector_01")
client.on_connect = on_connect
client.connect(BROKER, PORT, keepalive=60)
client.loop_start()

# Retain 메시지로 최신 상태 유지
client.publish(
    topic="pdm/line1/pump01/vibration",
    payload=json.dumps({"value": 3.14, "unit": "mm/s",
                        "ts": time.time()}),
    qos=1,
    retain=True,
)
client.loop_stop()
client.disconnect()
📥 Subscriber (paho-mqtt)
import json
import paho.mqtt.client as mqtt

def on_connect(client, userdata, flags, rc):
    client.subscribe("pdm/line1/#", qos=1)
    print("구독 시작")

def on_message(client, userdata, msg):
    try:
        data = json.loads(msg.payload)
        print(f"[{msg.topic}] {data}")
    except json.JSONDecodeError:
        print(f"[{msg.topic}] raw: {msg.payload}")

client = mqtt.Client(client_id="sub_influx")
client.on_connect = on_connect
client.on_message  = on_message
client.connect("localhost", 1883, 60)
client.loop_forever()   # 블로킹 루프
⚡ 비동기 구독 (aiomqtt)
import asyncio, json
import aiomqtt

async def main():
    async with aiomqtt.Client("localhost") as client:
        await client.subscribe("pdm/line1/#")
        async for message in client.messages:
            data = json.loads(message.payload)
            print(f"{message.topic}: {data['value']}")

asyncio.run(main())
🪦 Last Will + TLS 연결
import ssl, paho.mqtt.client as mqtt

client = mqtt.Client(client_id="pump_gw_01")

# Last Will 설정 (비정상 종료 시 브로커가 발행)
client.will_set(
    topic="devices/pump_gw_01/status",
    payload="offline",
    qos=1,
    retain=True,
)

# TLS 설정
client.tls_set(
    ca_certs="ca.crt",
    certfile="client.crt",
    keyfile="client.key",
    tls_version=ssl.PROTOCOL_TLS_CLIENT,
)
client.connect("broker.example.com", 8883, 60)

# 온라인 상태 발행
client.publish("devices/pump_gw_01/status",
               "online", qos=1, retain=True)
🗄️ MQTT → InfluxDB 파이프라인
import asyncio, json
import aiomqtt
from influxdb_client.client.influxdb_client_async import InfluxDBClientAsync
from influxdb_client import Point

MQTT_BROKER = "localhost"
INFLUX_URL  = "http://localhost:8086"
INFLUX_ORG  = "pdm"
INFLUX_BKT  = "sensors"
INFLUX_TOK  = "my-token"

async def main():
    async with InfluxDBClientAsync(INFLUX_URL, token=INFLUX_TOK, org=INFLUX_ORG) as influx:
        write_api = influx.write_api()
        async with aiomqtt.Client(MQTT_BROKER) as mqtt_client:
            await mqtt_client.subscribe("pdm/#")
            async for msg in mqtt_client.messages:
                parts = str(msg.topic).split("/")   # pdm/line1/pump01/vibration
                data  = json.loads(msg.payload)
                point = (
                    Point(parts[-1])          # measurement = "vibration"
                    .tag("line",   parts[1])
                    .tag("device", parts[2])
                    .field("value", data["value"])
                )
                await write_api.write(INFLUX_BKT, INFLUX_ORG, point)

asyncio.run(main())

SparkplugB
SparkplugB — 산업 IoT 표준 페이로드
Eclipse Foundation의 MQTT 위 산업 표준. 토픽 네임스페이스 + Protobuf 페이로드를 통일해 이기종 장비 연동 단순화.
SparkplugB 토픽 구조
토픽 네임스페이스
spBv1.0/{groupId}/{messageType}/{edgeNodeId}/{deviceId}

예시:
spBv1.0/factory1/DDATA/plc_gw_01/pump01

messageType:
  NBIRTH   - Edge Node 온라인 선언
  NDEATH   - Edge Node 오프라인 (Will)
  DBIRTH   - 기기 등록 + 전체 메트릭
  DDATA    - 변경된 메트릭만 전송 (효율적)
  DDEATH   - 기기 오프라인
SparkplugB 장점

📦 Protobuf 직렬화

JSON 대비 수십% 작은 페이로드. 타입 정보(Float/Int64/Boolean 등) 포함.

🏭 SCADA/MES 직결

Ignition(Inductive Automation), EMQX 등 주요 산업 플랫폼에서 SparkplugB 네이티브 지원.

🔄 상태 동기화

BIRTH 메시지로 재연결 시 전체 상태 복구. 온라인/오프라인 추적 표준화.

OPC UA + MQTT SparkplugB 조합이 현재 Industry 4.0 레퍼런스 아키텍처. OPC UA로 PLC 데이터를 구조화하고, SparkplugB/MQTT로 클라우드·상위 시스템에 전달.

MQTT가 HTTP보다 IoT에 적합한 이유는?
MQTT는 헤더가 최소 2 byte로 HTTP(수백 byte) 대비 훨씬 가볍고, TCP 영속 연결로 매 요청마다 핸드셰이크 없음. 비동기 Pub/Sub으로 수천 기기가 동시에 데이터를 올려도 단일 브로커가 처리 가능. 저전력·저대역폭(2G·위성) 환경에서도 안정적. HTTP는 요청-응답 구조라 실시간 Push가 불편하고 연결 비용이 큼.
QoS 1과 QoS 2의 실질적 차이와 선택 기준은?
QoS 1은 At-least-once — 네트워크 문제 시 재전송이 발생해 중복 수신 가능. DB 삽입에 멱등성이 있거나(InfluxDB 타임스탬프 중복 무시 등) 중복을 허용하면 QoS 1로 충분. QoS 2는 Exactly-once — 4-way 핸드셰이크로 중복 없이 정확히 1회 보장하지만 메시지당 4개의 패킷 교환. 제어 명령(Start/Stop), 금액 관련 이벤트처럼 중복이 치명적인 경우에만 사용.
Retain 메시지와 Last Will은 각각 언제 사용하나?
Retain: 최신 상태를 새 구독자에게 즉시 제공할 때. 예) 기기 온/오프라인 상태, 설정값, 최신 센서값. 새 대시보드가 연결되면 바로 현재 값을 볼 수 있음. Last Will: 기기가 비정상 종료됐을 때 브로커가 대신 "offline" 메시지를 발행. Keep-Alive 초과 → 브로커가 Will 토픽 발행. Retain과 Will을 조합하면 완전한 온라인 상태 추적 가능.
MQTT 브로커가 다운되면 어떻게 처리하나?
① 클라이언트 재연결 로직 구현 (지수 백오프). ② QoS 1·2 + Persistent Session(cleanSession=false)으로 오프라인 중 메시지 브로커가 보관 → 재연결 시 수신. ③ EMQX·HiveMQ 클러스터링으로 브로커 고가용성 구성. ④ 엣지 버퍼링: 브로커 연결 불가 시 로컬 큐(Redis/SQLite)에 임시 저장 후 재연결 시 발행.
MQTT 5.0이 3.1.1과 다른 점은?
① 이유 코드 확장(Reason Code) — CONNACK·DISCONNECT에 상세 오류 코드. ② 사용자 속성(User Properties) — 헤더에 임의 Key-Value 추가 (메타데이터). ③ 메시지 만료(Message Expiry Interval). ④ 공유 구독(Shared Subscription) — 여러 구독자가 로드 밸런싱으로 메시지 분산 처리. ⑤ 구독 식별자·Flow Control. ⑥ 향상된 인증(Enhanced Authentication) — SASL·OAuth 지원. 신규 시스템은 MQTT 5.0 권장.
토픽 설계 시 가장 중요한 원칙은?
① 왼쪽→오른쪽으로 범위 넓음→좁음 (pdm/라인/설비/지표). ② 와일드카드로 의미 있는 그룹 구독이 가능한 구조. ③ 클라이언트 ID를 토픽에 포함하지 않음. ④ 공백·특수문자 금지, 소문자 일관성. ⑤ 너무 깊은 계층 피하기 (4단계 이내 권장). ⑥ 수집·알람·제어 토픽을 분리해 ACL 제어가 쉬운 구조. 설계 이후 변경이 매우 어려우므로 초기 설계에 신중해야 함.
